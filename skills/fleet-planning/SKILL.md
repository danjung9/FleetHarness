# Implementation planning

Read `requirements.md`, `scope.md`, `research.md`, `.fleet/packet.json`, `.fleet/quality-contract.md`, `.fleet/solution-contract.md`, `.fleet/foundation-catalog.json` and `.fleet/foundation-guide.md`. The quality contract defines the exact JSON formats; do not invent a second schema. Publish the application architecture with `fleet_system_design`, mapping components to source files. Write `plan.md`, `test-matrix.md`, `foundation-plan.json`, `acceptance-plan.json`, `ux-spec.json`, `solution-contract.json` and `evaluation-plan.json`. Use acceptance schema version 2.

Choose the versioned foundation and computation pack that fit the domain specialist. Explain the choice in `foundation-plan.json` and include the foundation's complete runtime file list in `solution-contract.json`. The host copies the HTTP service, browser client and calculation modules after planning, before implementation; do not regenerate those files. An explicit custom template needs a concrete runtime incompatibility. Plan domain-specific computation and UI on top of the existing service, with one backend implementation shared by the interface and tests.

Define the smallest complete workflow, data contracts, dependencies, failure states and ordered tasks. Preserve every packet criterion ID and its provenance, including source requirements, evaluation criteria, deliverables and user criteria. Give each criterion a literal expected outcome and an implemented or deferred disposition. Implemented criteria must reference capability checks and/or applicable browser journeys; mandatory core capabilities must be implemented and evaluated; deferrals require an explicit reason and remain unverified. Keep missing domain facts visible and domain calculations separate from model-assisted explanation.

A primary requirement or expected deliverable may be deferred only if it truly needs real systems, real data or a person's authority. Lack of an official specification, format mapping or expert is never a reason. Plan a clearly labeled synthetic stand-in that demonstrates the whole requested workflow in the challenge's own vocabulary, with realistic invented sample data and the actual named outputs. Define the invented grammar, assumptions, independent answer key and literal browser outcomes before implementation. Require the UI, sample data, exports and evidence to state: synthetic, not validated against the real format. Synthetic behavior does not establish real-format validation or operational readiness.

For mock USMTF, plan extraction of frequency plans, crypto change-over windows and flight quarters onto a 24-hour timeline; a generic EVENT/TASK parser alone is incomplete. For departmental agents, demonstrate the named departments, negotiation and resulting schedule with synthetic inputs. Do not reduce either workflow to a generic form or chat. If a requirement explicitly demands a real connection, real-data validation or actual approval, preserve that unmet boundary and still demonstrate the synthetic workflow.

Start `plan.md` with a Primary deferrals section listing each deferred primary requirement or expected deliverable by canonical ID, original wording, concrete allowed dependency, withheld action and demonstrated stand-in, or explicitly state none. For every deferred JSON criterion use the quality contract's reason prefix: `real-system:`, `real-data:` or `human-authority:`, followed by that concrete explanation. Missing an expert is not approval authority. Keep the full inventory in `test-matrix.md`; a partial demonstration cannot count as a complete requirement. Require the same up-front disclosures in verification, the user guide and review summary. Never change a source requirement to make the synthetic slice appear complete.

Use `fleet-ux` to specify the intended user experience. Plan primary and recovery journeys with stable CSS selectors and literal observable assertions before the build agent sees the task. Use declarative steps from the quality contract, not executable test code. Pair browser journeys with Node tests for domain invariants and boundary cases in `test-matrix.md`. An outcome based on a separate planning session is protected from implementation drift; it is not independent SME ground truth.

Every primary deferral also requires the canonical quality contract's `syntheticCoverage`: explicit assumptions, known primary journey IDs and output names quoted from their source criteria, including the deferred criterion itself. Assert each output name with independent expected values after interaction. Keep the deferred criterion's own `journeyIds` empty. Use labeled synthetic examples in the requested input format; a substitute format remains incomplete. The independent judge checks that examples, answer keys, named outputs and the complete transformation match the card. Structural parser success cannot establish those facts. Preserve all existing disclosure, evidence and note-length requirements.

Choose a browser, CLI or service profile. Declare runtime files, entrypoints, locked dependencies and required model environment names. Define the computational objective and failure/abstention behavior. Plan distinct evaluation inputs with independently derived expectations, dataset provenance, baselines and thresholds. Use actual shared core logic for the runtime and tests; Node tests may invoke Python/service entrypoints. Model unavailability must be explicit. CLI solutions may omit browser journeys; browser/service solutions require primary and recovery journeys. The host holds evaluation answers outside the builder workspace. Include the public `invocation` object in `solution-contract.json`: `input`, `output` and `rules` must fully specify every action, field type, default/null behavior, response envelope, exact status/error string, ordering and error precedence. Interface details must never refer the builder to sealed evaluation cases. Derive held-out cases from these general rules; keep case-specific input/answer pairs only in `evaluation-plan.json`. Check that every expected response follows the public protocol before handing off.

Hand off once all planning artifacts exist. The host validates and freezes all JSON contracts immediately after planning; build and verification repair cannot weaken, rewrite or defer their expectations. Do not implement application code or claim tests passed during planning.
