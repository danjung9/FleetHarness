# Evidence and verification

Use the criterion IDs and provenance in `.fleet/packet.json`, including requirements, evaluation criteria, deliverables and user criteria. Read `.fleet/quality-contract.md` for the exact acceptance and UX plan formats. During planning, in `test-matrix.md`, state input, expected outcome and application test or planned browser journey for every criterion. `test-matrix.md` is frozen after planning, so record actual results and evidence locations in `verification.md`. Include negative and boundary cases specific to the recipe.

Tests must call actual application functions or exercise the real UI workflow. A repeated implementation assertion, a tool self-test, an empty test suite, source-string checks and a model's success statement do not demonstrate that users can complete a browser task. The separate planner defines literal outcomes before building; this reduces implementation drift but is not independent SME ground truth. The host freezes `acceptance-plan.json` and `ux-spec.json` after planning. Build and repair must never edit those contracts or replace a failed expectation with observed output. Record a suspected requirement error for a new planning run.

The desktop runner owns `test-report.json`, source hashing and acceptance browser screenshots/traces. It executes Node-compatible `.test.mjs` or `.test.cjs` tests and the frozen declarative browser journeys on desktop and narrow viewports. Supply application tests and record additional checks in `verification.md`. Do not edit `.fleet/`, frozen contracts or host evidence. Put temporary test data outside the source tree and clean it up. During build and verification, `fleet_browser` returns actual screenshots, page controls and console errors from the declared app. These development observations under `.browser-observations/` do not count as independent acceptance evidence. Use available host evidence and identify visual or manual checks you could not perform, including when the selected model cannot receive images.

The report tracks every criterion and journey. All implemented checks must pass before application review; an explicit deferral stays unverified. Keep `requirementsMet` separate from passing application checks so tested behavior cannot satisfy an unimplemented source requirement. Browser results cover the specified interactions, not complete usability, accessibility or operational validation. Missing browser runtime is a verification failure, not permission to claim a pass from Node results.

Deliver requested formats and primary work as requested. A stand-in is allowed only when an authoritative source is really missing; label it as a stand-in and record the unresolved gap in scope, planning and review evidence. Never count a stand-in as satisfying the original obligation or invent the missing authority.

Start `verification.md`, the user guide and the review summary with a Primary deferrals section, listing every deferred primary requirement or expected deliverable by canonical ID and original wording, allowed dependency, withheld action and demonstrated stand-in, or explicitly state none. Check the plan's `real-system:`, `real-data:` or `human-authority:` reason against the actual dependency; the parser checks only its structure. A missing expert is not approval authority. Preserve all deferred and partial outcomes as unverified; do not hide them behind passing test totals. If the frozen plan deferred defining behavior for an invalid reason, report the planning defect and require a new planning run rather than rewriting the frozen contract during repair.

Verify clean startup without seeded fictional records and exercise empty/setup/disconnected/error states. Supply fixture records explicitly through real application inputs for test journeys and preserve their synthetic provenance in development data documentation, tests and evidence. The product interface and application README should describe the actual application without synthetic-data, mock, demo or prototype branding. Users implement or configure external plugins and data connectors after the build; verify the adapter contracts and configuration behavior, and record unconfigured or unexercised external integrations separately. A stub or fabricated success cannot establish a real connection, synchronization or model response.

Browser/service builds additionally require Playwright UI flow exploration and host-recorded visual review. Open the app independently at desktop and narrow widths with `fleet_browser`, inspect the actual screenshots and visible controls, and choose manual actions from each observation to follow the useful task through its screens to a visible result. Use `action: "flow"` to inspect the host-recorded transitions and unexplored controls. Frozen journey replay, input echo and unchanged screenshots do not satisfy exploration. Use `fleet_visual_review` with actual capture IDs to record concrete expected/observed results and findings. After fixing findings, reopen the latest source, explore and recheck both widths, and explicitly resolve each finding with its actual change. A clean initial review still requires a fresh recheck. Each verification or repair session repeats the loop; passing Node/browser assertions does not waive it. The host validates capture origin, image integrity, runtime revision and unresolved findings, retains a private visual ledger across resume, and exports `visual-review.json`. Never write that report or claim a visual verdict from page text alone. Observed flow describes actual behavior and cannot redefine frozen expectations. These observations and agent judgments remain distinct from independent browser assertions and human review.

For claims from documents, retain source ID, revision, timestamp and exact excerpt/offset. `fleet_search_evidence` is lexical retrieval over supplied documents; it does not establish that a fact is true or applicable. Excluded, future-dated or stale evidence must not silently support a current claim.

Report generated, runnable, tested, reviewer-accepted and operationally validated separately. Name skipped, failed and unverified checks. A local test run cannot establish CAC integration, authority to operate, safe engineering decisions, device encryption, or a government-system connection.

When either Node or browser verification fails, use the host-granted functional repair allowance to fix the responsible implementation. Preserve failure evidence and frozen plans, then let the host rerun both gates. Record missing domain facts rather than inventing policy, equations or operational meaning to make a check pass.

## Computational capability evidence

Read `.fleet/solution-contract.md`. The host scores frozen cases with its own evaluators and runs the declared files in a fresh directory, installing declared locked dependencies. The builder must not recreate the sealed evaluation answer key. Core checks must pass before completing the application. Required capabilities cannot be deferred or bypassed by passing browser tests. The first primary user journey must also pass at both widths before expanding remaining application interactions. Core, primary-workflow and final verification have independent bounded repair allowances; consumed attempts and active time survive resume. Further automatic attempts require semantic progress, never rewritten expectations. Build tests freeze at the end of implementation, after the guide, and remain protected during verification and repair. Explicit ordinary Resume can authorize one additional final repair. Independent judgment retains its own repair and undo allowance. When service durability is required, exercise restartRuntime followed by expectServiceState and a visible retained outcome; use .runtime-data/ for writable service state and verify idempotency and recovery where required. Use the exact same computational implementation for runtime invocation and the interface. Missing dependencies, model configuration, failed inference, stale state or hardcoded sample outputs are failures. Assert complete response objects against the public `invocation` protocol, including literal statuses/errors and ordered arrays, with additional boundary inputs. On core failure, use the reported mismatch path to compare the implementation to that public protocol; do not infer success from a correct subset of output fields. Final reports retain dataset provenance, metric thresholds, observed scores, per-trial failures and runtime hashes. Synthetic cases demonstrate only those cases; human-reviewed domain validity remains separate.
