# Usable task flows

Read `.fleet/quality-contract.md` for the exact `acceptance-plan.json` and `ux-spec.json` formats. Follow the current phase: planning defines these contracts; building and repair implement them without changing their frozen expectations.

During planning, identify the audience, primary task and recognizable success outcome. Define each screen's purpose and primary action, plus empty, loading, error and success states, persistence, recovery and keyboard behavior. Choose stable CSS selectors for actions and assertions before implementation. Plan intentional primary and recovery journeys with literal expected outcomes, not arbitrary JavaScript or values copied from a later implementation. Include persistence or review boundaries in a journey when they determine task success.

Design and implement the actual application using its product name and task-focused copy. Do not add synthetic-data, mock, demo or prototype banners, badges or explanations to the interface or application README. Prepared fictional records belong in development and tests, not default runtime state. Start with actual configured or user-entered data, or a useful empty/setup state. Enter test records explicitly through the real application inputs when exercising acceptance journeys, and check clean startup separately.

Users implement or configure external plugins and data connectors after the build. Give each integration an actionable setup path, understandable configuration validation and honest disconnected, loading, error and connected states. Show a successful connection or result only after the actual operation succeeds; unavailable services must not produce fabricated activity, records or metrics. Keep fixture provenance and verification limitations in development/evidence artifacts, and document the extension points and connection steps in the application README.

When authoring `ux-spec.json` for browser/service applications, use version 2 from the quality guide. In architecture experiments, the shared plan specifies behavior and the candidate execution contract supplies the screen structure; the host compiles the UX contract. Follow the current phase guide instead of writing artifacts owned by another phase. Choose a task-based structure: a focused single task, sequential steps, list/detail, or a workspace with navigation. Explain that choice using the brief. Multiple HTML pages and service routes are supported, as are client-side views. There is no page-count target. In `plan.md`, sketch the screen map, transitions and each screen's main/supporting regions before implementation. Give every screen a stable ID, exact application route, unique root selector, primary action, layout, secondary content and narrow layout. Keep the shared navigation outside screen roots. A list and its selected detail can share one screen; separate full screens are mutually exclusive. Advanced options, diagnostics and raw records should be disclosed when useful to the task, with clear labels and a way back. Do not turn a feature inventory into stacked sections.

Start every frozen browser journey with `expectScreen` for the entry screen. Navigate through real links or controls and assert the destination screen; collectively cover every planned screen. `expectScreen` checks the route, visible screen root and absence or hiding of all other screen roots. Use `expectHidden` for secondary content when appropriate. Continue asserting actual domain outcomes: screen visibility cannot replace a literal task result or meaningful error recovery. Include return navigation, reload and preserved work in journeys when they are part of task success. CLI applications retain the version 1 UX description and no browser journeys.

Build a complete interactive workflow, not a static mockup. Make the next action and current status clear; use familiar task language and readable results. Keep technical IDs, raw JSON and diagnostic simulations secondary unless the audience needs them for its task. Use labeled native controls, visible keyboard focus and layouts usable at desktop and narrow widths. Explain why an action is unavailable and how to proceed.

Establish the planned navigation and screen layout before filling it with feature controls. Replace the starter's generic form as needed; declare every additional page/asset in the runtime manifest and explicitly serve service routes. Use relative links for static packages. Match each screen's primary action and hierarchy, preserve focus and unfinished work across transitions, and keep inactive screens hidden or unmounted. Inspect every screen reached by the journeys, including intermediate screens, at both widths. Review whether the main task is obvious, secondary controls compete with it, unrelated tasks are visible together, and the narrow layout preserves usable navigation. Report these as concrete visual findings with the relevant screen and capture.

Preserve unfinished work across ordinary interactions. When a flow includes review or submission, make saved versus unsaved content explicit and require a deliberate save or discard before approving different committed content. When conflicts must be resolved, show the competing values and let the user select or edit the result before confirming; preserving revision IDs alone does not make a conflict review usable.

During build and verification, determine the actual UI/UX flow with the Playwright-backed `fleet_browser`. Open the declared app at desktop and narrow widths. Inspect the screenshot and returned controls before choosing an action, then inspect the resulting screen after each click, input or navigation. Trace a useful task from entry through its visible result; explore return paths, secondary content and recovery. Use the observed controls instead of guessing selectors from source or merely replaying the frozen journey. Compare the observed transitions with the intended task and fix missing affordances, dead ends and unclear feedback. Edit source with workspace tools, then call `open` again and explore the updated runtime. Each action returns an image and page observations; an image-capable model is required for visual inspection. CLI applications have no browser preview. Do not claim visual checks when images are unavailable.

For browser/service apps, this loop is mandatory. Record an initial review at **both** widths with `fleet_visual_review`: use the returned `captureId`, describe `expected` behavior from the frozen UX/acceptance contract and `observed` results from the actual image, list `findings`, and supply `resolutions` (empty initially). Record both initial reviews before fixing the source. Fix findings, reopen the app, capture both widths again and record rechecks, explicitly resolving each returned finding ID with its `change`. Even a clean initial review needs a fresh capture and recheck at each width. A finding can only be resolved with a later capture of changed runtime files at its viewport. Every build, verify and repair session must complete its own loop; earlier sessions and screenshots of stale source cannot satisfy it. Missing, stale or modified captures and unresolved findings block completion. The host saves `visual-review.json`; do not author or alter it. Stay within the existing stage and repair budget.

The host separately executes the frozen browser journeys and returns results, screenshots and traces in its test report. Interactive observations under `.browser-observations/` help development; they do not replace independent acceptance evidence or authorize changing frozen expectations. Use returned evidence to repair the responsible implementation within the separate bounded core, primary-workflow and final repair allowances. Browser checks establish specified interactions; human review still assesses clarity, usefulness and fit for the intended users.

## Sailor bar

The person does not code. Every primary workflow must be completable through visible controls, with clear forms or imports for supplying the task inputs and an honest empty state before data is supplied. Do not make them edit JSON, use a terminal, or convert units or times by hand. Show dates, times and quantities the way the person would say them, for example Tue 0900, never minute offsets, epoch numbers or internal IDs. Anything the person must change to do the task, such as a roster, a rule or an input record, gets a form. Give outputs a person can use directly: a readable screen, a printable page or CSV. JSON may be offered as an extra, never as the only form.

Put the person's main task first and make it complete without coaching, using only what is on screen. Setup, signing keys, protocol exercises and evidence belong behind a clearly labeled section, not mixed into the watchstanding controls.
