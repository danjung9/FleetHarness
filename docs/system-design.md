# Live system design

Every new build asks the planning agent to publish the application architecture early through `fleet_system_design`. The tool validates 1–12 major components, their source files, and up to 24 directed, labeled connections. It saves `system-design.json` in the run workspace and publishes the same definition to the UI. Components describe the application being built, rather than AppYard's build pipeline.

The implementation and verification agents call `fleet_component_progress` as they work. Each update is broadcast through the existing application state subscription and persisted locally. Statuses are **Planned**, **Building**, **Generated**, and **Blocked**. Interrupted work displays **Stopped** or **Blocked**, depending on the run outcome. A new run or an edited brief clears the old design.

**Generated** means the agent reports implementation and every mapped source file exists and is nonempty. It does not certify functionality. Independent test results remain application-wide, and human review remains required. Repair can move a generated component back to Building. Component progress is stored outside the source workspace so updates cannot invalidate verification hashes. The architecture file itself is included in those hashes and the exported source bundle.

In the desktop app, open **Build → Plan → System design** after the planning agent publishes the architecture. Components are grouped by responsibility across Interface, Application logic, Data, and Integrations. Select a component to highlight its connections and inspect its responsibility, current progress, source filenames, and incoming or outgoing relationships. Select a relationship in the inspector to navigate to the connected component. **Focus connections** dims unrelated components so a single part of the system is easier to trace.

Use **Zoom in**, **Zoom out**, and **Fit diagram** to explore the architecture, or **Expand system design** to use the full screen. Drag a blank area of the canvas to pan an enlarged diagram, or scroll inside its panel. Component buttons and toolbar actions also support keyboard navigation. The details inspector can be hidden and restored without losing the selected component. At narrower widths, including beside the build phase list, the inspector and controls adapt to the available panel width; large diagrams stay inside the canvas. The diagram also provides planning and explanatory empty states when embedded before a design is available.

Planning must publish a valid design before advancing. Build and verification stages require component completion reports, with the existing single completion attempt used for missing reports. These reports are model-authored; files existing is a necessary check, not proof of implementation quality. The planner should name simulated integrations explicitly and keep diagrams focused on roughly 3–8 components.

Run `npm test` for validation, persistence, cancellation, and source-integrity checks. Run `npm run test:system-design` for the deterministic local-provider workflow, live UI transitions, repair, reload, stale-design clearing, interrupted and empty states, zoom and pan, expansion, connection focus, and inspector navigation. It also checks a twelve-component architecture across all four component kinds, long labels and source paths, and desktop/minimum layouts with activity open. Screenshots are saved in `output/playwright/`. The fixture does not call a hosted model or establish hosted-model output quality.
