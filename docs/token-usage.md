# Token usage

The workspace indicator adds the recorded usage of every project. Project details show its cumulative total and the current run. Counts include build agents, independent planning reviews, project-lead conversations, shared experiment planning, and every candidate, including failed or unselected candidates. Starting a fresh build keeps previous usage. Selecting a candidate does not add its tokens a second time.

`Project.tokenUsage` stores cumulative snapshots per model session, with a unique session ID, run ID, source, model and timestamps. Sessions survive `state.json` reloads. Experiment worker projections also persist their session records; the parent merges them by ID and recovers any missing merge at startup. Comparison selection and forgetting learning history do not reset the parent usage already recorded.

Pi counts come from the installed SDK's `getSessionStats().tokens`, which includes assistant responses, tool-reported usage, compaction and usage entries. The runner reads after Pi appends completed messages and again when a prompt settles or the stage closes. It also retains reported streaming usage before cancellation can prevent the final append, reconciling that lower bound with persisted totals instead of adding the response twice. Adapters without session statistics use assistant/tool message usage. Pi's uncached input, cache reads and cache writes are combined into input tokens. Cached reads remain a subset of input for display.

Codex counts come from the bundled 0.166.0 app-server's `thread/tokenUsage/updated` notification, using `tokenUsage.total`. The notification shape was verified with that executable's `app-server generate-ts` command. Thread totals replace the previous snapshot across repeated events and credential reconnections. Input already includes cached input; output already includes reasoning, so neither is added again.

Counts are provider-reported consumption, not the context-window size, subscription quota or a billing estimate. Updates arrive at response boundaries, not with every generated token. A session without a usage report is unreported rather than zero. Legacy builds and conversations are not backfilled, so the interface labels the totals as recorded usage and notes that earlier activity may be missing. Completed responses with explicit zero are distinct from unreported usage. Pi's initialized all-zero values on failed or aborted responses remain unreported; positive partial usage is retained. Interrupted requests retain usage received before shutdown; providers may not report the partial request, and work outside AppYard is excluded.

Validation: `tests/token-usage.test.mjs` exercises normalization, cumulative deduplication, Pi persistence timing and compaction, reported zero, cancellation, save failures, Codex reconnection, fresh builds, conversation accounting and reloads. The token accounting case in `tests/experiment-service.test.mjs` verifies both candidates, shared planning, duplicate projections, selection and crash recovery.
