# Tools for an automatic software factory

Research date: November 4, 2026. Scope: taking a requirement through research, implementation, verification, delivery, and subsequent maintenance. This is a capability assessment and implementation recommendation, not a benchmark or an integration claim. Recommendations below are engineering judgments based on the inspected FleetHarness working tree and linked primary documentation.

**Recommendation:** extend the existing harness with browser verification, source-backed research, isolated execution, reproducible application environments, and Git/CI integration. Add durable recovery and release operations as the factory becomes unattended. Keep domain tools selective. A reliable factory needs both tools agents can invoke and host services that enforce completion and preserve evidence.

**What the current code establishes.** The working tree was changing during this review; the observations include local changes around commit `f72c5dc`, not just the committed or packaged release. Source inspection was used to establish these capabilities; application builds and new integrations were not executed for this research.

**Tools to add first.** The order reflects expected value for FleetHarness, not measured performance. Effort is relative: small means an adapter to an existing API/CLI; medium adds sessions, artifacts, and UI support; large changes execution or delivery architecture.

The recommended browser starting point is the existing Playwright dependency with a thin adapter and host test runner. Microsoft's [MCP repository](https://github.com/microsoft/playwright-mcp) also describes CLI-plus-skills as suitable for coding agents and MCP as useful for persistent exploratory sessions. That is a documented design tradeoff, not a measured advantage in FleetHarness. Compare the interfaces on the same tasks before choosing.

Screenshot support also needs a transport check: the current Codex custom-tool adapter forwards text content only. Adding a screenshot-producing tool will not by itself deliver pixels to that model. Verify image handling end to end for each backend, with structured page inspection available when image input is unavailable.

**The harness needs a broader application contract.** Define profiles such as static browser app, Node web service, and Python service. Each profile should declare install, build, start, health, test and package commands; entry points; exposed ports; runtime/tool versions; service dependencies; and expected artifacts. Validate this manifest in the host. The existing static profile can stay available. A package manager or Docker command alone will not remove the current single-file requirements, preview routing restrictions, artifact limits, or Node-only verifier.

Use one implementation of application logic in production and tests. For example, build the single-file output from tested source modules when that packaging is required. The present request to keep inline code and separate testable core consistent leaves room for the tested implementation to differ from the delivered UI.

**A compact proposed agent interface.** These names describe new capabilities; they are not currently registered tools. Split broad operations into smaller schemas if pilot runs show ambiguity.

| Proposed tool group | Agent-visible operations | Host-owned result or control |
| --- | --- | --- |
| `fleet_web_search`, `fleet_fetch_source`, `fleet_query_docs` | Search, read a source, look up a library/version | Source IDs, excerpts, timestamps, bounded responses and retrieval errors |
| `fleet_process_start`, `fleet_process_status`, `fleet_process_stop` | Start a declared build/service/test process, inspect logs, cancel | Run-scoped process ID, health/exit state, bounded logs and guaranteed cleanup |
| `fleet_browser_*` | Navigate a run preview, inspect, interact, capture | Isolated session, page references, screenshots and console/network evidence |
| `fleet_repo_*`, `fleet_ci_*` | Inspect changes, checkpoint, create an authorized PR, read checks | Base/head revision, diff, PR/check IDs, conclusions and raw evidence |
| `fleet_verify` | Request a named verification suite, inspect its failures | Host runs the configured suites and records source/test/environment fingerprints |
| `fleet_request_input`, `fleet_task_update` | Raise a material ambiguity; record task dependencies/progress | Persisted question and response, resumable state, verifiable task completion |
| `fleet_release_*` | Request a preview/release, inspect status, request rollback | Target and artifact digest, configured release policy, health evidence and operation ID |

Every mutating call should identify the run/workspace and return a durable operation ID when work outlives a response. Record actual failures distinctly from missing prerequisites, cancellation, timeout and partial results. Bind retries of external mutations to an idempotency key. Carry short summaries in model context and retain large logs, screenshots, reports and downloads as artifacts.

The host should own capabilities, credentials, budget ceilings, process termination, verification conclusions and release policy. Agents can request those operations and inspect outcomes. Browser and fetch tools should treat retrieved text as source data, and enforce destination policy outside the model. Ordinary containers need deliberate configuration; [Docker's security documentation](https://docs.docker.com/engine/security/) identifies daemon access and configuration as part of the boundary. Do not expose the host Docker socket to generated code just to make integration tests convenient; provision test services through the host provider or an isolated worker.

Use native SDK calls or pinned CLIs where they already fit. [MCP](https://modelcontextprotocol.io/docs/learn/architecture) is a useful interoperability protocol for external tools/context, but adding it does not implement durable workflows, verification, or isolation. The current Pi path explicitly excludes generic MCP tools, so MCP support would need a deliberate allowlisted adapter. Preserve phase-specific tool selection and apply the same capability policy across backends.

**Challenge-specific additions should load on demand.** These are reusable application dependencies or task-specific tools, not prerequisites for every factory run.

| Challenge need | Candidate and condition for adoption |
| --- | --- |
| Documents, scans and tables | [Docling formats](https://docling-project.github.io/docling/usage/supported_formats/) and [OCR support](https://docling-project.github.io/docling/) are candidates for ingestion. Preserve source/page provenance and evaluate extraction against labeled examples. Synthetic message parsing does not establish OCR or real-format accuracy. |
| Richer scheduling | [OR-Tools CP-SAT](https://developers.google.com/optimization/cp/cp_solver) supports integer constraint models and explicit solution statuses. Evaluate when scale/objectives exceed the current feasibility search; preserve the distinction between feasible, optimal, infeasible and unknown. |
| Offline replication | [PouchDB/CouchDB](https://pouchdb.com/guides/replication.html) is already a recipe candidate for replication. Test real durable edits, disconnection, reconnection and conflict review. It requires a schema/transport decision, not a direct replacement for the current revision calculator. |
| Approved knowledge corpora | [SQLite FTS5](https://sqlite.org/fts5.html) is a candidate for local full-text indexing. Add authenticated connectors when a source is specified. Evaluate retrieval quality before introducing embeddings or a vector database; permissions and freshness remain separate requirements. |
| Parsers, reconciliation and other invariants | [fast-check](https://fast-check.dev/) provides generated inputs for JavaScript/TypeScript properties. Use it for invariants such as replay idempotence, ordering independence and invalid-input handling. Correct properties and independent expected results still need to be specified. |

Repository search and package inspection also deserve a standard execution image: provide a fast text search command, Git and the selected runtime/package tools. Add semantic symbol/reference lookup when work on existing large repositories demonstrates that text search is insufficient. Design-file connectors, asset generation, spreadsheet/PDF authoring, load testing and platform-specific signing should be selected by the actual deliverable. There is no evidence here that all should be permanent tools in every session.

**Suggested sequence and proof of value.** This is an implementation roadmap, not a claim that the integrations have been built.

1. Add browser interaction and host browser acceptance tests to the existing static profile, plus search/fetch/documentation tools to research. Maintain a source ledger. Establish the execution-provider interface and test isolation before expanding package installation or unattended execution.
2. Add one full-stack profile, supervised services, reproducible dependency installation, Git checkpoints/PRs, CI ingestion, disposable database tests and scanners. Build the same revision in a fresh environment. Keep environment/test artifacts outside writable application source where appropriate.
3. Add persisted task recovery, pending questions, usage budgets and resumable external operations. Introduce a workflow service only when the local model no longer meets recovery/concurrency requirements.
4. Add one deployment target, release health checks and rollback. Extend to more targets or multi-worker orchestration only after the end-to-end loop is measured.

Use the existing message, scheduling and offline pilots, plus one small database-backed application, as an evaluation set. Keep task inputs and independently reviewed acceptance checks fixed. Run baseline and changed harness configurations with the same model/settings and comparable limits; repeat to expose variability. Measure requirement pass rate, false-success rate, human interventions, wall time, model/tool usage, estimated cost where prices are configured, and repair/recovery success. Report distributions and failures rather than selecting only successful examples. The decision criterion is more verified completed tasks per unit of time/cost, not more tool calls.

| Required experiment | Evidence that the addition works |
| --- | --- |
| UI defect that core unit tests miss | Break a button binding or display transformation. Host browser checks fail, retain a trace, and pass after a real repair. |
| Version-sensitive research | Given a pinned dependency, the report cites an opened source matching that version or explicitly reports the gap. A search snippet alone cannot satisfy the check. |
| Runtime lifecycle | Start app/database, wait for health, exercise persistence, then cancel. Verify processes, ports and temporary resources are reclaimed. Test mount/network/resource boundaries separately. |
| Independent acceptance | An implementation with a deliberately wrong business rule fails a host-controlled fixture even if its agent-authored unit suite passes. The builder cannot rewrite the controlling fixture. |
| Reproducibility and CI | A fresh checkout/environment installs from locks and produces the expected tested artifact. CI evidence and review reference the delivered revision. |
| Recovery and external side effects | Kill the worker after a checkpoint and after an external operation succeeds but before acknowledgment. Resume from recorded state without duplicating the operation. |
| Budget enforcement | Force a repair loop and slow tool. The host stops them at configured limits and records why; missing usage data is visible. |
| Release and rollback | Deploy the tested artifact to the selected preview target, detect an injected health failure, and restore the previous artifact. Test data/migration compatibility separately; reverting code alone is not a database rollback. |

The smallest useful next implementation is Playwright browser access, host browser tests, and a search/fetch adapter. Isolated execution is the prerequisite for widening execution authority. Replacing the current coding backend or installing another orchestration framework is not required to test these improvements.
