# Repeatable application foundations

Research date: November 4, 2026. This records the source-backed selection rationale for FleetHarness. The repository now implements original internal foundations; the external starters below remain candidates and were not installed or benchmarked. See [the operator and developer guide](application-foundations.md) for the implemented behavior and [the software factory research](software-factory-tools-research.md) for the broader roadmap.

**Implemented approach:** the host materializes a versioned, repository-owned application foundation after planning and before the builder runs. The accepted solution contract and agent recipe determine the runtime and domain adapters. The builder extends the existing routing, request validation, frontend/backend wiring, and computation boundary. Application-specific behavior and acceptance tests remain agent work.

The existing recipes mostly share the same application plumbing. Different model providers do not require different frontend stacks; recipe capabilities, computation language, persistence, offline requirements, and delivery format should determine the foundation. The coding backend determines which editing tools and instructions the agent receives.

## Starter selection

The decisions below are engineering judgments for this repository. External projects are candidates for a separately tested foundation release, not live downloads during every build.

| Candidate | Decision and fit | Primary evidence |
| --- | --- | --- |
| Repository-owned HTML/ES modules + Node service | **Implemented as `node-service` 1.0.0.** The frontend calls a local HTTP API backed by one computation module. Recipe packs copy existing FleetHarness domain implementations into the delivered application. It needs Node 22.19+ and no package installation or framework build. This is the lowest operational overhead for the current pilots. | Local `harness/foundations.ts`, `templates/node-service/`, `templates/registry.json`, and `electron/solution-runtime.ts`. |
| Repository-owned HTML/ES modules + Python service | **Implemented as `python-service` 1.0.0.** The same frontend transport calls a Python computation boundary. It needs installed Python 3.10+ and uses the standard library; Python is not bundled with the desktop app. Physics selects this by default, with domain computation intentionally unimplemented. It is a local prototype foundation; Python documents that `http.server` is not intended for production hosting. | Local `harness/foundations.ts`, `templates/python-service/`; [Python HTTP server documentation](https://docs.python.org/3/library/http.server.html). |
| Vite `vanilla-ts` / `react-ts` | **Adapt when the UI warrants it.** Use one pinned official preset as a maintained UI foundation. Compile during foundation/application build, then deliver the built assets alongside the compute service. Vite is frontend tooling; the template does not supply domain computation or persistence. | [Official presets](https://vite.dev/guide/), [backend asset integration](https://vite.dev/guide/backend-integration.html), [MIT license](https://github.com/vitejs/vite/blob/main/LICENSE). |
| Fastify `create-fastify` / `fastify-cli` | **Adapt for richer Node APIs.** Suitable when a project needs multiple routes, schema validation, and plugin structure. Generate once in the foundation maintenance workflow, keep the generated files and lockfile, then add the FleetHarness computation contract. Avoid running integration mode over user work: its documentation identifies files it overwrites. | [Official generator](https://github.com/fastify/create-fastify), [CLI generator and standalone-server support](https://github.com/fastify/fastify-cli), [schema validation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/), [MIT license](https://github.com/fastify/fastify-cli/blob/main/LICENSE). |
| Full Stack FastAPI Template | **Defer wholesale import; adapt for Python-heavy, database-backed products.** It already joins a React/Vite UI to a Python API, with PostgreSQL, authentication, testing, and deployment infrastructure. That breadth is useful when actually required, but excessive for a small parser or calculator. Its Bun/uv locks and multiple services need explicit build/install/service support beyond the present npm/pip runtime contract. | [Official template and MIT licensing](https://github.com/fastapi/full-stack-fastapi-template), [feature list](https://raw.githubusercontent.com/fastapi/full-stack-fastapi-template/master/README.md). |
| Electron Forge Vite + TypeScript | **Defer for generated apps.** Consider for a separately maintained desktop application foundation when native integration is required. Reuse the existing FleetHarness packaging path first. The official documentation still labels its Vite support experimental and allows breaking changes in minor releases. | [Official template](https://www.electronforge.io/templates/vite-+-typescript), [MIT license](https://github.com/electron/forge/blob/main/LICENSE). |
| Copier | **Defer until template upgrades become a recurring need.** It renders parameterized projects and supports updating generated projects. A small built-in deterministic renderer is enough for the first few foundations and avoids another runtime dependency. | [Official documentation](https://copier.readthedocs.io/en/stable/). |

## Match the agent's recipe to computation

The implemented catalog uses two service foundations with recipe overlays rather than ten unrelated stacks. A runtime profile chooses transport; a recipe chooses reusable domain modules and synthetic example inputs. Acceptance cases must still be derived independently from the agreed requirements.

| Agent recipe | Foundation and backend boundary |
| --- | --- |
| `messages` | Input/review UI calling the existing extraction module; preserve source offsets. Add OCR/file parsing only after a real format and evaluation set are supplied. |
| `scheduling` | Planning UI calling the existing deterministic feasibility solver. Select a Python adapter when [OR-Tools scheduling](https://developers.google.com/optimization/scheduling) is needed for scale or richer constraints. |
| `readiness` | Dependency editor and result view calling the existing graph calculator. Keep unknown durations and invalid graphs explicit. |
| `knowledge`, `cyber` | Search/evidence UI calling existing approved-corpus retrieval. Add [SQLite FTS5](https://sqlite.org/fts5.html) when an indexed local corpus is justified. Cyber-specific execution remains a separate authorized adapter. |
| `offline`, `workflow` | Record/revision UI with persistence and conflict review adapters. Existing reconciliation is reusable computation; it is not durable storage. Consider [PouchDB/CouchDB replication](https://pouchdb.com/guides/replication.html) only with a chosen schema, transport, and conflict workflow. |
| `governance`, `physics` | Governance defaults to the Node service and physics to the Python service, both with `computePack: custom`. These recipes have no implemented domain tool; a ready application shell must not imply validated calculations or governance. |
| `fielding` | The default recommendation is Node with a custom compute boundary. When the brief supplies a working application, planning should select `templateId: custom`, preserve that application, and declare its runtime. Do not replace working code with a new scaffold. |

The implemented browser client and host service evaluator call the same `/api/invoke` endpoint, which imports `compute.mjs` or `compute.py`. Application tests must exercise that same computation module. A test-only implementation or a host tool that disappears from the exported package does not satisfy backend integration. Browser-only and CLI profiles use the explicit custom-template escape hatch. Offline requirements still need their own tested storage and recovery behavior.

## Reproducibility contract

The implemented `foundation-plan.json` records the selected template/version, compute pack, and reason. `templates/registry.json` pins bundled template assets and compiled computation-module hashes. Before implementation, the host checks those assets and records the original materialized file hashes, aggregate fingerprint, file count, and byte count in `foundation-lock.json`. Source is editable; the host checks that plan and provenance remain unchanged. Materialization refuses to overwrite differing existing files. The agent receives a compact catalog and guide rather than the entire template in its prompt.

For future externally sourced foundations, also record upstream revision/license and generator version. Runtime versions and dependency locks belong in the execution evidence and application package. Preserve the original foundation records when resuming work; do not regenerate over edited application files.

For dependencies, commit exact versions and full transitive locks. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) fails when manifests and locks disagree. For Python, [pip hash checking](https://pip.pypa.io/en/stable/topics/secure-installs/) requires pinned, hashed dependencies, including transitives. Never put floating `@latest`, default-branch clones, or CDN dependencies in the generation path. An external foundation update is a new reviewed version, not a mutation of previous applications.

Current runtime constraints matter: `prepareSolutionRuntime` copies an allowlist into a temporary package, accepts npm v2/v3 registry locks without workspaces/local links, installs production dependencies with scripts disabled, and installs hash-pinned Python wheels. It does not run an arbitrary frontend build or orchestrate a Compose stack. Framework foundations therefore need prebuilt artifacts or an explicit build-provider extension. Its sanitized environment and clean package are not an operating-system sandbox.

## Prove reduced work

Run the same message, scheduling, offline, and backend-service tasks with fixed model/settings and independently reviewed acceptance cases. Compare foundation-enabled runs against the existing baseline across repeated trials. Record input/output tokens, time until a working backend call, retries, verified requirement completion, and human interventions. Count reused foundation bytes separately from model-authored bytes; byte reuse is not a token-savings measurement.

Every promoted foundation should reproduce its file hashes from identical inputs, start in a fresh runtime, exercise the actual UI-to-backend request, and pass independent known-result cases against the packaged computation. Test resume without overwriting edits and missing-runtime/dependency failures. Token savings remain an expected benefit until measured; passing scaffold tests establishes plumbing, not completion of an application's requirements.
