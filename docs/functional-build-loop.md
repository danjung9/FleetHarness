# Building and repairing complete workflows

New builds evaluate the computational core, implement the first frozen primary user journey, and run that journey in fresh application packages at desktop and narrow widths before completing the remaining interface and user guide. The first primary journey should therefore represent the smallest useful task, including its required input, computation, saved state and output. CLI applications use their callable-core checkpoint because they have no browser journey.

The early workflow report is development feedback, not final acceptance. The host saves `.quality-evidence/workflow-report.json`, screenshots and traces, and keeps a trusted report snapshot outside the builder workspace. Editing the diagnostic copy cannot change the gate. The final verifier still runs all developer tests, capability evaluations, browser journeys and visual review against the final files in separate clean packages.

Core, primary-workflow and final verification each allow at most three automatic repairs and fifteen minutes of active repair work, including the following check. Each gate reserves its own allowance, so an early computational defect cannot consume the final repair opportunity. Existing stage and experiment deadlines remain upper bounds. Two successive observations without semantic progress stop a gate earlier. Progress is fewer failed host checks, higher scores, or more completed frozen journey steps without new failures or regressing existing metrics. New output text, timestamps, file edits and different screenshots alone do not establish functional progress.

The host checkpoints a repair reservation before calling a model and settles elapsed time afterward, including normal cancellation. Resume retains attempts and consumed time. After an unclean process interruption, a pending lease consumes its remaining allowance: the host cannot establish how much unrecorded work ran. A new build starts fresh allowances. Older checkpoints with only `repairUsed` debit one attempt in their recorded phase when first entering the new policy. Frozen contracts and expected outcomes remain unchanged throughout repair.

For service persistence, planning can use `restartRuntime` followed by `expectServiceState` with an `input` read operation and exact JSON `expected` result from the public invocation protocol, then assert the visible outcome. The host terminates and replaces the actual application process while keeping its package, dependencies, data directory and URL. Browser storage survives, which is why the separate host invocation is needed to detect a UI masking lost server state. Services store writable data in `.runtime-data/` relative to their working directory; standalone applications create it on startup. The directory cannot contain declared source files. Browser-only applications use reload to test browser storage and cannot request service lifecycle steps.

Plan repeated submissions to prove idempotency and induced failures followed by retries to prove recovery when the requirements need those behaviors. External integrations still need configured, authorized test operations and actual evidence; these local lifecycle checks do not establish remote-system behavior or operational readiness.

Regression tests exercise actual process replacement, persistent versus memory-only services, independent state inspection, repair progress and caps, interruption, immutable expectations, and gate ordering. `npm run check` validates the whole repository offline. Improving generated application success rates remains an empirical question: compare the same representative briefs under the old and new process using the live factory benchmark, and report verified workflow completion, repair effort and token/time cost separately from these harness regressions.
