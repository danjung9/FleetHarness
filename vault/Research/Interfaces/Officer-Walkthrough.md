# An officer's first ten minutes

## Bottom line

[A] An officer who does not code is likely to understand Studio's challenge collection before understanding the original's build graph. [A] The original's three-field custom form may be quicker once the officer knows what to request. [E] In the supplied browser previews, neither route reaches a running agent or generated app. [R] Start the demo in a prepared desktop Studio, supply a synthetic example, and let a technical teammate handle setup. [R] Keep the officer's job to choosing the task, correcting the brief and checking the result.

## How to read this walkthrough

[A] This is a cognitive walkthrough, not an observed usability test. The officer is a hypothetical training coordinator trying to turn fictional room/time requests into a draft schedule with visible conflicts. They know their task but not coding, agents or model providers. [A] Minute ranges allocate an orientation exercise; they are not measured completion times or a promise that generation finishes in ten minutes.

[E] The starting screens are the supplied PNGs at 1440 by 900. Other screens are reconstructed from `src/App.tsx`, `src/studio/Studio.tsx`, `src/studio/brief.ts`, `src/ModelSettings.tsx`, `src/PhaseDetails.tsx` and `src/SystemDesign.tsx` at `0f175a8`. All these paths are under `/Users/mukul/Documents/CDAO/FleetHarness`. [E] Quoted interface labels below are reproduced for this requested label audit. [A] Each stated comprehension problem is a hypothesis to check with a person, not a claim about every naval officer.

## Vocabulary and choice audit

[E] This table covers the visible technical vocabulary in the supplied screens and the traced continuation. [A] Ordinary words can still be ambiguous in a new product; this is a list of likely comprehension risks, not tested comprehension scores.

| Exact label or token [E] | Why it may interrupt the officer [A] | Plain-language treatment [R] |
| --- | --- | --- |
| "Flow", "Build flow", "System design", "Agents", "Auto-repair" | Process, architecture and automated labor are competing explanations of what is happening. | Default to current task, what is complete, what happens next and how to stop; offer technical details separately. |
| "Intake", "Research", "Plan", "Build", "Test", "Review", "Deliver", "Queued" | Who performs each step, and which steps need the officer? Queued can imply someone is already processing it. | Identify software versus human work and whether any run has actually started. |
| "Assigned skills", "Global tools", "Phase-specific tools", "Harness tools" | These sound like roles or equipment, but describe agent permissions and backend operations. | Collapse into technical details; retain a short readable permission summary before running. |
| "fleet-intake", "read", "write", "edit", "bash", "fleet_get_challenge" | Internal capability identifiers and a command shell name. | Explain that software can read/change local files and execute programs. Never mistake hiding these labels for reducing permissions. |
| "Inputs", "Outputs", "requirements.md", ".fleet/packet.json", "scope.md", "Ready to advance when" | File extensions and a hidden directory are implementation details; the exit rule may look like a human sign-off. | Present the problem brief, scoped plan and next required decision, with filenames available to reviewers. |
| "Model settings", "Build engine", "Codex · ChatGPT subscription", "Pi · model providers", "Provider", "API key", "Model", "Refresh connection" | Several technical/account choices precede a useful result. | An authorized technical owner prepares the approved connection. Keep inspectable connection state and Stop available. |
| "Workspace storage", "Workspace", "Open workspace", "Browser preview" | Local browser, desktop project and generated app storage are different. | State where this brief is saved and which actions work here. |
| "NF / 11", "Pilot pick", "Offline & edge", "skills", "Your build crew", "Host" | Catalog IDs, project curation, network jargon and machine roles can sound like official status. | Show the task name, label sample scope, explain operator responsibility and avoid implying authorization. |
| "Overview", "Requirements", "Expected deliverable", "Evaluation criteria", "Resources", "Links" | Several long fields require the officer to translate a need into a software specification. | Prefill the synthetic task; ask what should happen, what must never happen and how to check it. Keep original source detail available. |
| "Generate software", "Download brief JSON", "Choose brief JSON", `npm run studio` | The first is a consequential action; the others assume file-format and terminal knowledge. | Confirm execution scope; put browser-to-desktop transfer behind a clearly named handoff to a technical operator. |
| "Interface", "Application logic", "Data", "Integrations", "Generated" | A component diagram and its completion labels do not prove task correctness. | Show the user-visible outcome and distinguish implementation progress from passing tests. |
| "Independent test output", "exit code", "skipped", "Approve prototype", "Delivered" | Technical execution evidence can be confused with an independent judgment or authorized operational release. | Pair each fixed sample with expected result, actual result and reviewer decision; explain exactly what approval and local export do. |

## What would count as a win in an officer session

[R] Ask the officer to find the training task, change one assumption, explain what is saved, identify what approval permits and find Stop. Then have them use a prepared generated app on one valid and one conflicting synthetic case. Record prompts for help and active minutes, including review. [R] Test intake separately from the generated app; a beautiful catalog and a running factory are not evidence of saved deckplate effort. [A] No participant, time saving, error rate or completion result is established by this walkthrough.
