# FleetHarness interfaces side by side

## Bottom line

[R] Use Studio as the officer-facing entry, after adding the original's start confirmation. [E] Both interfaces reach the same execution, verification, approval and local export implementation. [E] They have separate renderers and saved work, and Studio does not reuse the original's structured activity viewer. [E] The supplied browser screenshots demonstrate discovery and editing, not a running software factory or a delivered application. [R] Keep the original available for technical inspection while narrowing the demo to one useful, independently checked result.

## Scope and evidence

[E] Read-only Git inspection identified branch `mvp`, commit `0f175a8ce346521c4462fc134d40c0973eac1323`, and a clean worktree during review. All repository paths below are relative to `~/Documents/CDAO/FleetHarness`. [E] Visual findings use the seven supplied screenshots under `~/Documents/CDAO/Fleethacker-Vault/Research/FleetHarness-MVP/screens`; they are browser previews with no agents running. [E] Build and review behavior below is traced from source and test definitions, not exercised in this review. [A] Audience fit is a design hypothesis, not an officer interview result.

## What is actually shared

[E] Both renderer trees import `ModelSettings`, `PhaseDetails` and `SystemDesign`, shared `Project`/`FleetAPI`/stage types, and the same catalog, recipes and phase definitions. Paths: `src/App.tsx:1`, `src/studio/Studio.tsx:1`, `shared/types.ts`, `harness/catalog.ts`, `harness/recipes.ts`, `harness/phases.ts`.

[E] Their desktop APIs resolve to the same preload bridge, IPC handlers, Store, factory runner, engine adapters, artifact access, verification and preview/export code. `electron/pi-backend.ts` now implements the common factory for both Pi and Codex; its filename does not mean Studio or the original is limited to Pi. Intake, research, planning, implementation and verification have phase contracts, followed by human review and host delivery. Paths: `electron/main.ts`, `electron/preload.cts`, `electron/pi-backend.ts:110`, `electron/codex-session.ts`, `electron/verification.ts`, `electron/storage.ts`, `harness/integration.ts`.

[E] Divergence is substantial above that bridge: navigation, layout, status names, intake/editor logic, browser fallback state, source-link handling, activity rendering, review forms and start permission. `src/studio/Studio.tsx` does not wrap `App.tsx`. They also have separate entry points and styling: `src/main.tsx`, `src/styles.css`, `src/studio/main.tsx`, `src/studio/studio.css`, `studio/index.html`.

## Shared review limitations that the visual comparison must not hide

[E] The host executes generated tests independently of a model's claim, but the agents can author and revise those tests. `electron/verification.ts` checks outcomes and source consistency, not whether every officer requirement was tested. [R] Add human-owned expected results for the selected demo application.

[E] The backend records notes, timestamp and source hash, but no authenticated reviewer role; the checkbox is a renderer interaction, not a backend identity check (`electron/main.ts:72`). [E] Export verifies before opening the folder dialog, then copies mutable files without a second destination hash check (`electron/main.ts:80`). [R] Keep prototype approval language and coordinate any export-integrity fix with the architecture work. These shared concerns do not favor one renderer over the other.
