# The officer's first ten minutes

## Bottom line

[E] The current app helps someone commission and inspect software, rather than immediately perform a watchstanding task. [E] Studio replaces much of the original pipeline-first presentation with challenge browsing and a structured brief, but retains provider setup and technical acceptance work. [A] A noncoding officer could sponsor a brief with help, but independent safe operation is not established by the source. [R] Let a technical teammate operate the factory and give the officer one prepared app with one useful job.

## Conditions of this walkthrough

[E] This is a cognitive walkthrough from source at `~/Documents/CDAO/FleetHarness`, `mvp`, `f72c5dc15aa6c34d2b9080c1c0b87742230cc16e`. No screen was launched, timed or tested with a person. [A] Times below allocate a hypothetical ten-minute visit; they are not measured durations or a promise that a build finishes. [A] The persona is an officer who knows the work problem and does not code; an actual billet, command process and training need have not been validated in this seat.

[E] The clone advanced to `0f175a8` during review. This walkthrough remains pinned to `f72c5dc`; it does not evaluate the later interface/backend additions.

## Original desktop journey

| Visit segment [A] | What source puts on screen [E] | Knowledge demanded and likely friction [R] |
| --- | --- | --- |
| Before minute 0 | `docs/desktop.md` names a prepared mac arm64 app; `package.json` otherwise requires a development/build toolchain. `src/api.ts` makes browser-only execution unavailable. | Someone must supply the correct app and tell the officer whether this is desktop or a browser preview. Installing Node, packages or a development server is technical support work. |
| 0 to 1 | `src/App.tsx:App` defaults to the flow view of a saved starter challenge. `Factory` displays seven stages, a repair loop, a run identity/model line and test status. | The first task is understanding software production. The displayed message/scheduling/offline starters are briefs, not ready tools. A noncoding user must distinguish a proposed app from a working one. |
| 1 to 2 | `Intake` offers catalog, custom and starter routes. `RequirementsForm` asks for a title, problem statement and one measurable outcome per acceptance line. | The officer must choose the right source case, decide a narrow deliverable and write acceptance tests in prose. A familiar operational problem is being translated into a software specification. |
| 2 to 4 | `Settings` requires a provider, a model and available authentication. It shows a key field, optional remembered storage, runtime information and a local storage path. | The officer must know which company/account the key belongs to, which model the event permits, whether existing authentication is suitable, and whether to retain the key. Configured status does not confirm a successful request. The key owner must do this themselves. |
| 4 to 5 | `App` opens a start confirmation describing model/provider use, shell permissions, lack of an OS sandbox and possible charges. | Consent here requires understanding both data leaving the laptop and code running on it. No separate command-by-command permission flow is shown. This is a consequential technical trust decision, even with synthetic data. |
| 5 to 7 | `Development` can open the system design, live activity, source folder and application iframe. Reload retrieves the preview after `index.html` exists. | The officer must distinguish generated components, passing tests and a usable app. Watching file operations or architecture does not help them complete the underlying job. There is no measured completion-time estimate. |
| 7 to 8 | `AgentSessions`, `Artifacts` and failure banners expose provider errors, tool calls, source files and test output. | Troubleshooting can require knowing file paths, Node tests, missing artifacts, provider failures and when a fresh run is needed. The app has no named human support contact. |
| 8 to 9, if finished | `Evidence` asks the operator to try the app, assess agent-written tests, read limitations, acknowledge inspection and enter notes. The host checks report/source integrity. | A noncoder cannot be assumed to judge test adequacy or correspondence between tested core logic and the displayed HTML. Keep mission review with the officer and code/test review with a technical reviewer. |
| 9 to 10, if approved | Export opens a folder chooser and creates a source/evidence bundle. `DELIVERY.md` is generated by the host. | The officer must locate/open `index.html`, understand that exporting source is not deployment, and distinguish technical test instructions from everyday use. No approved device-install or official-release process is supplied. |

The workspace begins with a design view and offers activity, preview, files and review tabs. | Studio omits the original desktop's start confirmation about shell access, provider disclosure and charges. ## Every technical decision exposed in the reviewed flows

[E, `src/App.tsx`, `src/studio/Studio.tsx`, API adapters and backend] The technical touchpoints are: desktop versus web mode; installation/runtime; provider; model; key ownership and source; optional key retention; provider data transfer and cost; permission for local file/shell work; interpreting recipe skills/tools and candidate integrations; translating the job into acceptance criteria; architecture/component status; generated source and artifact paths; test output and coverage; repair/failure diagnosis; restarting rather than resuming; choosing the export destination; and opening the delivered HTML or rerunning its Node tests. [R] Preconfiguration can remove several from the officer's visit, but doing so transfers real setup and review work to the team and must be counted.

[E] `src/SystemDesign.tsx` renders the application architecture, and `electron/system-design.ts` validates file presence before component completion. It does not establish source correctness. `shared/activity.ts` produces more readable tool events for the original dashboard; Studio displays raw log text in its activity tab. [R] Keep these views available for the technical operator, behind the officer's task rather than as the primary proof of value.

## Stop and recovery from the officer's perspective

[E] The original header and Studio workspace show stop actions during a build. Backend cancellation and quit handling are implemented, as traced in [[Research/FleetHarness-MVP/What-Exists]]. Closing the window on macOS does not itself end the application; saved runs do not resume automatically after restart. [R] Put stop beside the primary action, explain that earlier file changes remain, and give a technical escalation contact. Prove this with a live stalled run, including cancellation during generated tests, before saying a user can reliably recover.

## A useful acceptance exercise

[R] Prepare one generated app in advance, with a documented technical review and frozen synthetic answer key. Give an uncoached noncoding reviewer a new permitted input and ask them to obtain, check, correct, save and reopen one result. Record time to first useful result, help requests, mistakes, total review/conversion effort and whether they can identify unresolved work. Then separately ask a sponsor to create a factory brief and record the technical help it takes. These are two different user jobs and need separate evidence.

[R] For Thursday, target the Council Officer's 90-second task exercise on the finished app and a ten-minute supported brief exercise on the factory. Do not report either as passed until observed. A local synthetic teammate trial should be identified as such.
