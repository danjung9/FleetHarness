## Concrete integration risks from the local source

1. **Fixed people versus negotiated allocations.** Each request carries exact `people`; the primitive only chooses candidate starts. Qualification coverage is collective: every required qualification must be held by at least one assigned person. It does not choose people, enforce distinct role headcounts or check qualification expiry. Alternate personnel assignments and departmental counterproposals need explicit domain handling; duplicate mandatory requests cannot stand in for mutually exclusive alternatives.
2. **Constraint boundaries and time.** Starts are nonnegative integer minutes relative to a caller-defined epoch. Requests must fit entirely inside one operational window and one availability window for each person; adjacent windows are not merged. Source overlap comparisons implement half-open intervals. Cross-midnight work, week boundaries, time-zone conversion and carry-in duty must remain explicit. Prior duty history is not an input to this primitive.
3. **Fatigue semantics.** Rest is checked between every pair of supplied assignments for each person, and `maxMinutes` sums duty across the supplied horizon. It is not a rolling daily budget or fatigue science model. Invented demonstration policies must be labeled and must not be presented as owner-approved SFTRM rules. Richer rolling windows or historical obligations require additional logic and evidence.
4. **Resources and operations.** Any shared resource string is exclusive during overlap. There is no resource inventory, capacity greater than one, resource-specific availability, travel/setup time or per-drill operational window field. Domain validation must catch unknown resources and represent allowed candidate windows without implying unsupported capacity enforcement.
5. **Recurrence completeness.** No recurrence, completion history, due dates or mandatory/optional distinction exists in the input. All submitted requests must be assigned to return feasible. Mandatory recurrence requires explicit occurrence expansion and completeness/deadline checks outside the primitive, including carry-in and week-edge obligations. A feasible subset cannot certify SCH-04.
6. **Search scope and diagnostics.** Up to 24 requests, 200 people, 100 candidate starts per request and maxNodes up to 200,000 are visible limits. The default is 50,000 nodes, not a performance guarantee. Ordering is fewest candidates then ID; starts are numerically sorted. First feasibility is not preference optimization. `infeasible` concerns supplied choices; `budget_exhausted` leaves feasibility unknown. Invalid inputs throw errors. Preserve these distinctions. Explanations are capped observations from failed search, not a minimal conflict proof; feasible results return an empty explanation list, so a negotiation history cannot be recovered from success diagnostics alone.
7. **Empty and incomplete inputs.** Local arrays can be empty; the primitive can find an empty request set feasible. It does not know what the PB4T week is required to contain. The application must not translate empty feasibility into completed mandatory training or enable acceptance for missing policies/occurrences.
8. **Review and UI are separate capabilities.** No weekly board, loading heatmap, negotiation transcript, editable review state, stale-result invalidation, local persistence or acceptance authority is supplied. User edits must not retain acceptance of a previous input revision. Constraint-change requests cannot silently relax hard policies. Human operator acceptance remains distinct from feasibility and from a synthetic acceptance record.

## Options and open questions handed forward

The strongest locally evidenced reuse option is the supplied primitive for bounded feasibility, with its constraints disclosed. OR-Tools remains a conditional alternative when scale or a specified objective justifies evaluation; select neither a release nor an integration mechanism without evidence. Neither option supplies SFTRM semantics, a departmental negotiation workflow, or the requested UI automatically.

Concrete questions remain: What explicit synthetic negotiation priorities and alternate personnel choices demonstrate all named departments? Which invented recurrence/history and fatigue examples cover the full week without implying real policy? How are per-drill windows, role counts, resource availability and prior duty represented without losing constraints in translation? What does the one-click action optimize, if anything beyond feasibility? What scale and objective would warrant evaluating OR-Tools, and with which verified license, pinned version, runtime and benchmark? Which local review revision is being accepted, and what changes invalidate it? For eventual operational validation only: which owner supplies applicable SFTRM revision, approved fatigue rules, authoritative data and actual operator approval?

These questions do not block a complete labeled synthetic demonstration. Preserve the UI/data/export/evidence disclosure: synthetic, not validated against the real format or real SFTRM rules. No operational systems, real crew data, deployment, publication or release is authorized.
