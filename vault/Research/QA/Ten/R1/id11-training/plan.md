# Synthetic PB4T feasibility planner, implementation handoff

Planning phase only, 2026-11-04. The architecture was published using `fleet_system_design` before the remaining planning documents. Required outputs are `system-design.json`, this plan, `test-matrix.md`, `acceptance-plan.json` and `ux-spec.json`. No application code, application test execution or browser inspection is part of this phase.

## Scope and authority

Implement the smallest complete offline workflow: load synthetic departmental requests; see the original collision; edit and explicitly save hard constraints; find a complete feasible allocation; independently audit it; review weekly times and numeric personnel loading; locally accept the exact proposal; retain work across reload and export it. The primary audience is the training coordinator. This is a feasibility demonstration, not an operational scheduling service.

Source authority and full exact canonical requirements/provenance are retained in `test-matrix.md`. The packet's `acceptance` array is canonical: seven IDs, no alias entries, no supplied event evaluation criteria or extra user criteria. Source capture is 2026-11-04, upstream revision/time unknown; source URL is https://cdao.hackathon.maximus.com/event/norfolk/use-cases/11. Research records hashes/excerpts and distinguishes local retrieval from independent domain evidence. This plan adds no source claims or invented policy.

SCH-01, SCH-02 and SCH-03 are planned as implemented against explicitly supplied synthetic inputs. UC11-1, SCH-04, SCH-05 and DELIVERABLE11-1 remain deferred in full. The demonstration contributes slices to these broad requirements without establishing them. In particular, no departmental collaborating agents, actual operator signoff, SFTRM rules, or optimization objective are supplied. `requirementsMet` must remain separate from passing demonstration checks. Planned outcomes are independent of later implementation but are not SME ground truth.

## Architecture, dependencies and runtime

See `system-design.json` for five application components and labeled data flows. Deliver a self-contained `index.html`: inline styles, classic JavaScript, no fetch/import, CDN, runtime toolkit, fonts, server, install step or network. Opening the file must work. Use ordinary native controls and DOM text rendering; never interpret entered strings as HTML. No image assets are needed.

Research's local primitive is a behavioral reference for a bounded fixed-person candidate model. Implement the application-owned engine against the explicit contract below; do not copy modules with unverified redistribution terms. Keep `.fleet/` unchanged. Build may use its assigned calculation tool as a reference only, never verification. No planning-phase solver call is authorized or required. OR-Tools is deferred: license/release/runtime/benchmarks and objective semantics are unverified; adding it would violate this dependency-free slice.

Place pure domain functions in a clearly delimited inline classic script in `index.html`, exposing a single `PB4TCore` object. `scheduler-core.cjs` is a Node-only adapter that reads that designated script and executes it in a minimal `node:vm` context, then exports the actual functions. Do not duplicate domain algorithms in a second file. `scheduler.test.cjs` calls those functions through the adapter using Node's built-in runner and assert library. This links Node evidence to the delivered inline domain code, while frozen browser journeys prove UI wiring. Merely comparing source strings or testing a toolkit is insufficient. Browser UI code must call this same `PB4TCore` interface; no separate browser solver. Include an independently structured validator, not a second invocation of the search feasibility predicate.

Recommended core functions: validateInputs, findSchedule, auditSchedule, computeLoads, compareProposals; state transitions may also be exported for meaningful revision tests. Domain calculations are deterministic, locally reproducible and separate from explanations. Use template explanations grounded in actual inputs/violations. No model service, chat or model-assisted explanation is necessary; future model prose cannot alter constraints, assignments, audit or approval.

## Frozen demonstration fixture and data contract

The following example is a planning fixture, not copied solver output. Both requests start at minute 540 originally and require Alex and Room A, so there is exactly one shared-person collision and one shared-resource collision. With a required rest of 30, the sole feasible alternative is Engineering at 630: Damage Control runs [540,600), Engineering [630,690). Total Alex duty is 120, minimum gap 30. These arithmetic expectations precede implementation.

- `schemaVersion: 1`, `classification: synthetic`. One week, epoch `2026-11-02T00:00:00Z`, timezone `UTC`, horizon [0,10080), integer minutes, half-open intervals. UTC avoids implied local/DST policy. Display Monday through Sunday, week of 2 November 2026; show UTC on allocations. Reject crossing the week boundary.
- `operatingWindows: [[540,1020]]`. An interval must fit wholly in a single supplied window; do not merge adjacent windows silently. Resource registry includes `room-a` (Room A), exclusive capacity one. Greater capacities and resource operating calendars are unsupported and must be rejected if supplied.
- People: `alex`, name Alex, Engineering, qualifications `[EOOW,FPL]`, availability `[[540,1020]]`, `minRestMinutes:30`, `maxMinutes:120`; `bea`, name Bea, Combat Systems, qualifications `[TAO]`, same availability, rest 30 and budget 120. Qualifications are declared valid for the entire synthetic horizon, not verified credentials. Required qualification coverage is union over exact assigned people; no distinct billet-count claim.
- Requests in deterministic order: `dc`, title Damage Control, department Damage Control, duration 60, candidates `[540]`, originalStart 540, people `[alex]`, qualifications `[EOOW]`, resources `[room-a]`; `eng`, title Engineering, department Engineering, duration 60, candidates `[540,630]`, originalStart 540, people `[alex]`, qualifications `[FPL]`, resources `[room-a]`. All supplied requests are mandatory within this model; no omitted request can count as complete. IDs are unique and stable. These are explicit occurrences, not recurrence expansion.
- Prior commitments default to an explicit empty array labeled No prior commitments supplied. Support immutable existing intervals within the week, containing people, resources, start and end, in duty, rest and collision checks. Do not claim knowledge of duty outside the supplied horizon. Unsupported rolling/daily policy or carry-in before the epoch requires an explicit limitation, never inferred compliance.
- `maxNodes:1000` default, integer 1 to 200000. Deterministic request order is the listed order and candidate starts are ascending. Count each attempted candidate placement as one node. At budget 1, the root's first request can be placed but the second cannot be attempted, so status is budget_exhausted. Do not reinterpret this as infeasibility or precompute overlap infeasibility before this budget gate. Static missing qualifications/empty eligibility may be identified as infeasible without search; malformed data is invalid input.
- Limit editor instances to 12 requests, 20 starts per request, 50 people; duration 1 to 480; starts/endpoints integer in horizon. Validate nonempty people and request lists, known person/resource IDs, nonempty qualifications where needed, unique IDs, positive durations, valid windows, nonnegative rest and budgets. Support zero-rest and zero-duty boundaries; unsupported/ambiguous data is rejected explicitly.
- Solver result: `status` feasible/infeasible/budget_exhausted; complete `assignments` only for feasible status; `nodesVisited`; deterministic observations and scope limitations. Invalid input has structured field errors, not a fourth feasibility status. A feasible result must pass independent audit before it is exposed for local review. Audit checks exact request coverage/uniqueness, supplied starts, durations, qualifications, windows, prior commitments, every shared interval pair and horizon duty. Reject bad solver results and suppress acceptance.
- Local state: `draft`, `committedInputs`, integer `revision`, `currentProposal` bound to that revision, `lastAcceptedProposal`, `reviewAcknowledged`, `dirty`. Local storage key `pb4t-synthetic-v1`; storage schema versioned, validate on load. Export current audited proposal as UTF-8 pretty JSON with filename `pb4t-proposal.json` and literal `"classification": "synthetic"`.

## Workflow and state transitions

Start empty with Load synthetic week. On empty storage loading the fixture commits revision 1; no solver runs until Find feasible schedule. Loading over work needs an explicit replace/cancel prompt; a reset creates revision 1 for that reset workspace. Save inputs validates the draft and increments revision only for changed, valid content. Failed validation preserves draft and committed state. Persist draft separately after ordinary edits, retaining raw field strings until validation. Discard changes deliberately restores committed data. Never let automatic rerender erase unsaved fields.

Any dirty draft requires save or discard before solving or accepting a different committed proposal. Clicking Accept local proposal while dirty reports the frozen review error; the control remains actionable so it can explain that requirement. Saving a changed draft invalidates the current proposal and review acknowledgement; historical accepted content stays visible as historical. On revision 2 or later the review status reads Revision N needs a new feasible proposal and review. A failed recalculation shows No current proposal to review. It never restores the prior accepted proposal as current. Local acceptance requires a complete audited current proposal and the review checkbox; acceptance is not an authorized operator's signoff. Reload restores the explicit revision and local acceptance without treating drafts as committed.

Show requested and proposed time/person/resource values together; let the coordinator edit candidates and exact assignments through labeled forms and board-linked editor controls, then save/recalculate. No silent manual override or relaxation. Show a personnel heatmap with numeric minutes, budget and percentage, zero loads and accessible legend; do not rely on color. The collision and allocation selectors have narrow literal text, not surrounding card copy. Detailed explanations are observations, not minimal conflict proofs.

All screen purposes, primary actions, empty/loading/error/success, persistence, recovery and keyboard rules are frozen in `ux-spec.json`. The primary sample controls must be available without advanced JSON editing. In an advanced input section use exact labels matching unit semantics: minimum rest (minutes), duty budget (minutes across supplied week), availability end (minutes from epoch), candidate starts (comma-separated minutes). Keep technical diagnostics secondary.

## Failure, performance and human-review boundaries

Preserve in-memory work on unavailable storage/quota or corrupt saved data; show a visible storage warning, offer export, and require confirmation before discarding corrupt state. Local files may have browser-specific storage behavior; this is a delivery risk to test, not permission to claim persistence without browser evidence. Show an announced loading state before bounded synchronous work and always clear it. Limits control exposure but do not constitute a latency benchmark. Download behavior and both viewports require host evidence.

Required domain review remains: owner policy revision/effective dates, periodicity applicability/history/deadlines, distinct billet requirements, qualifications/expiry, prior-duty accounting, resource capacity, allowable reallocations, objective/quality bounds, representative scale and the accepting operator. No credentials, live systems, operational records, publication or deployment are involved. No requirement is operationally validated by this prototype.
