# Reuse research, OPTASK extraction and timeline

Research date: 2026-11-05. Phase: research only. No application, implementation plan, acceptance contracts or foundation files were created. Requirements, scope, packet and supplied fixtures are preserved.

## Primary deferrals and evidence boundary

No primary synthetic workflow requirement is proposed for deferral. The complete demonstration must extract **frequency plans, crypto change-over windows and flight quarters event times** from invented mock USMTF raw text and produce a synchronized 24-hour visual schedule. Missing real-format specifications or SME mapping do not justify omitting that behavior. Actual USMTF compatibility and operational accuracy remain unverified. Use the exact visible label: **Synthetic; not validated against the real USMTF format.** Owner approval remains necessary at the later delivery/deployment gate.

## Recommendation

**Adapt `node-service` 1.0.0 with computation pack `messages`.** This is the best bundled foundation, rather than a complete domain solution. The catalog supplies a dependency-free Node HTTP adapter, computation boundary, browser client and error handling. Retain and extend the host-materialized shared backend; do not rebuild setup. The host copies it after planning. Its actual server/client implementation and foundation lock are not yet available, so their behavior and exact hashes cannot be verified here.

The messages pack supplies useful original-text/UTF-16 evidence conventions and validation primitives, but its parser recognizes only generic EVENT/TASK lines. The prepared fixtures instead use `SYN-OPTASK/1` with MSGID, FREQPLAN, CRYPTO, FLIGHTQ and ENDMSG sets. Adapting the computation is substantial domain work: message boundaries, all three categories, field evidence, duplicate quarantine, strict timestamps, ship/day selection, clipping, review issues and export consistency are absent from the baseline. Renaming generic events would be incomplete.

The principal architectural mismatch is MSG-05: the stock client POSTs to a local service, whereas a disconnected browser must parse **new** input and export its reviewed result. A running localhost service and a cached last result do not prove that. A feasible reuse direction is one browser-compatible deterministic module used by both backend invocation and the browser's offline execution, potentially served through a service-worker request handler. This is a research option, not a selected implementation design. It must preserve backend reuse, one computational implementation, declared runtime files and host evaluation. A browser-only custom foundation is a permitted escape hatch only if planning demonstrates concrete incompatibility with the service; it is currently unnecessary. The offline pack is record reconciliation, not this solution.

## Concrete integration risks and planning handoff

1. **Format fidelity and evidence:** source records must remain unchanged, including CRLF and astral Unicode. Use zero-based, end-exclusive UTF-16 spans into raw input. Field values, message identity and category require evidence; derived UTC/duration/clipping values need explicit derivation. Preprocessing into a substitute grammar would invalidate offsets and lose domain fields.
2. **Validation differences:** prepared grammar excludes seconds, implicit rollover, point intervals and timezone defaults. Duplicate message/record IDs quarantine every collision. Unsupported potentially relevant sets create visible issues while unrelated valid events survive. Baseline generic warnings and permissive item emission cannot satisfy this.
3. **Selection and display:** preserve source-order extraction/export; exact ship matching and half-open UTC-day intersection are fixed synthetic assumptions. Retain full overnight endpoints while clipping only the visual segment. Overlapping frequency/crypto/flight categories need readable lanes and a narrow-screen list.
4. **Review and export:** raw draft, extracted output and reviewed output are distinct states. Edits/reparse must invalidate stale results and review status. Unsupported text remains inspectable; acknowledgement cannot validate an order. Export must retain original input, evidence, warnings, synthetic label and current selected ship/day. Do not derive an extracted message ID from a fixture ID for invalid/empty input; fixture export IDs are metadata, as the README explains.
5. **Offline and persistence:** service workers or browser execution must run the same computation used by `/api/invoke`, with no parallel test-only parser. Define first-load readiness, disconnected new-input parsing, reviewed download, reload limits, storage failures and cache/version mismatch. No bundled foundation claims offline persistence. Host acceptance needs actual disconnected-browser evidence in addition to ordinary browser journeys.
6. **Data and testing boundary:** fixtures include nominal, other ship, overnight/day boundaries, equivalent zones, Unicode/CRLF, 320-line dense text, empty/missing-zone/impossible-date/incomplete/unknown/malformed/reversed/point inputs, duplicate records/messages and mixed valid/unsupported input. Reuse exact prepared samples and literal issues. Planning must establish separate held-out cases and a complete public invocation protocol; runtime must calculate results from raw text, never read expected outputs. Fixture consistency checks/tool self-tests are not application verification.
7. **Runtime and packaging:** retain catalog service files, foundation-lock and pack files in the later runtime allowlist; ship no `.fleet` dependencies or answer keys. Node local version meets the minimum but clean-runtime host compatibility is unverified. No connectors, HTTP application endpoints, browser workflows or exports were exercised in research.
8. **Acceptance completeness:** preserve all 13 canonical IDs: UC12-1, MSG-01 to MSG-05, DELIVERABLE12-1, DESC12-1, DESC12-2, SUMMARY12-1, SCOPE12-3, SCOPE12-5, SCOPE12-7. Structural headings/source aliases remain traceability obligations, not extra features. Later planning must map every ID without claiming real-format validity, and require actual core, application and browser checks plus visual review at both widths.

Future operational questions remain open: actual USMTF message types/revisions and field mappings, amendment precedence, addressing/timezone policies, retention, operational approval authority and representative accuracy thresholds. They do not block a complete explicitly synthetic workflow. No material user decision is missing for research; no clarification gate is needed. Generated research is the only completed output; application runnable/tested/reviewer-accepted/operationally validated statuses are all unestablished.
