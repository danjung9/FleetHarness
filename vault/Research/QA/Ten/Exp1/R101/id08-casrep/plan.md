# CASREP Command implementation plan

All five canonical criteria are planned as implemented **synthetic** outcomes. No implementation or verification has occurred. The source requirement for NWP formatting is preserved, but the stand-in is not validated against the real format or operational rules. Actual identities, command authority, classified handling, Navy messaging, Microsoft 365, authoritative format validation and deployment are external readiness dependencies; no connector or operational action is part of this prototype. Passing prototype checks cannot establish that all original operational requirements are met.

Display “SYNTHETIC, DEMONSTRATION ONLY, NOT FOR TRANSMISSION” permanently and in exports, plus “Not validated against real CASREP format or operational rules.” No model or external service is needed.

Synthetic validation assumes required nonempty ship/hull, serial, equipment, casualty, impact, corrective action, JSN and restoration estimate (UTC or literal UNKNOWN); a valid UTC casualty time; type INITIAL/UPDATE/CORRECT/CASCOR; category 2/3/4. Linked types require an earlier synthetic report reference (the companion fixture SYN-CASREP-0000 is available). CASCOR additionally requires actual restoration UTC and closure narrative. These are fictional demonstration rules, not NWP or maintenance policy. Show companion previews for all four types. Give each type, category, field and preview an accessible label. ISO UTC text inputs make the frozen values independent of browser locale.

Originator submission is its approval. Sequential holders are Division Officer → Department Head → Engineer Officer/CHENG → XO → CO. Only current holder decides; all six roles may comment, return to originator with a required reason, or approve/forward when their turn permits. Originator return means retain draft. CO approval requires a checked explicit confirmation and is called simulated release. Comments never change content or approval validity. Retain failed decision attempts in audit. The primary journey includes Division Officer comment, return “Specify the affected cooling loop”, originator revision “CHWP-2 failed. Auxiliary cooling loop B.” and a fresh full route.

The secondary competing-amendments simulator must be plainly labeled. No clock-based winner. Resolution creates one child referencing both heads, retains branches and invalidates all earlier approvals. Both source values remain inspectable after reload and export. No real sync adapter or upload scheduler is implied. Research considered replication alternatives; no bespoke transport is justified for this single-browser simulation.

## Data contract and guards

Use one schemaVersion=1 localStorage envelope under `casrep-command-v1`: records, immutable revisions, comments, decisions, audit, releases, lifecycle links, selected record and separate unfinished form buffer. Record: immutable id, serial, current revision/head IDs, holder, status, related record, lifecycle state. Revision: unique id, recordId, parents[], actor, role, createdAt UTC, value (canonical JSON string or null tombstone), digest. Report content includes all scope fields above. Canonical serialization uses fixed key order; approval binds exact canonical content, revision ID and digest. Use a deterministic content digest available in classic local JavaScript, and compare canonical content as well; this is an integrity binding, not a cryptographic signature. No external script dependency.

Decision: id, recordId, revisionId, digest, actor, role, action, reason, timestamp. Comment is a separate immutable event bound to revision. Audit includes successful/failed transitions, returns, comments, invalidations, resolutions, cancellations and releases. Simulated actors have stable fictional names (e.g. Sailor Example, Officer Example); neither names nor local times are authenticated. Released snapshot captures content, exact message, revision, decisions and release metadata; immutable thereafter.

States: draft → review at each holder → simulated release; any return → returned draft; any content save creates revision → draft at Sailor/LPO with all previous approvals historical/inactive; conflict blocks routing/release until resolved. Dirty form blocks decisions with the exact frozen error until deliberate save/discard. Initial save does not silently submit. Unchanged save must not manufacture a content revision. Decisions must reference current revision and all previous fresh approvals in order. Require no conflict, clean form, current CO, complete approvals and release confirmation for final release. Repeated submission/release cannot duplicate events.

Model post-release amendments as new linked records, default UPDATE and fresh approvals, retaining the original released snapshot. A released CORRECT supersedes the linked report only upon its own simulated release; CASCOR closes the related casualty only on its own release. Cancellation is an explicit confirmed local draft lifecycle action, retaining history; released records can only receive a separately routed linked cancellation proposal, never be erased. Expiry is a manually confirmed synthetic archival marker with reason, never an inferred Navy deadline. Archived/cancelled drafts cannot route; a new linked draft is required. Preserve supersession/closure/cancellation/expiry metadata separately from report type. These lifecycle assumptions must appear in guidance and Node tests.

## Failure behavior, monitoring and human boundaries

Preserve drafts across role changes, invalid fields, navigation among sections and reload. Disable duplicate actions only while a local commit is pending. Failed saves show no success; corrupted storage must not masquerade as an empty valid workspace. Display exact transition/validation errors specified by acceptance-plan.json. Reset/load over existing work requires deliberate confirmation; default cancel. Render report text as text, never HTML. Enforce reasonable lengths (2,000 characters per narrative, 100 per reference; at most 5,000 revisions) with visible errors and no partial writes.

Every approval, return, reconciliation and release is an explicit human simulation. Prohibit real data, classified processing, credentials, network requests and background release. Monitor only local state, validation, conflict flags and audit. Escalation is a visible instruction to stop and record an unresolved question for the future owner; no notifications are sent. Provide Stop demonstration / Resume controls; stop blocks mutations and preserves work, downloads remain available. Confirm clear-local-data separately with history-loss warning. Closing the tab stops execution; nothing runs remotely.
