## Recommendation

**Adapt `node-service` 1.0.0 with `offline` computation pack.** This is the best listed foundation for this workflow specialist: dependency-free local HTTP service, browser client and one shared computation module match the scoped deterministic record workflow. The offline pack supplies usable immutable-revision reconciliation. Its mismatch is substantial but explicit: it supplies no CASREP renderer/validator, chain-of-command state machine, approval invalidation, audit transaction, durable persistence, authentication or transport. Those are application responsibilities; selecting the pack does not establish them.

The host materializes the pinned foundation after planning. Starter source and foundation-lock.json are not yet present, so actual adapter behavior, per-file hashes, runtime compatibility and end-to-end execution are not inspected or tested. The catalog and guide establish the advertised interface only. Retain the selected foundation's files and extend its shared backend rather than reproduce scaffolding. Both UI and host invoke raw JSON through `/api/invoke`; application tests must call that same core. `/health`, HOST/PORT handling, runtime allowlist and Node 22.19+ remain contract constraints for planning. Embed the needed exact fixture inputs in public/index.html; do not fetch local fixture paths or duplicate computation in the browser. This reconciles the self-contained sample-data requirement with the required local service; it does not promise browser-only operation while the service is stopped.

## Exact fixture reuse and integration risks

**Adopt the supplied synthetic data unchanged.** inputs/manifest.json has `sources: []`, mode synthetic. The fixture inventory has five editable starting drafts: INITIAL, UPDATE, CORRECT, CASCOR and INITIAL without JSN. All start DRAFT; preset loading must not fabricate completed approvals. The three linked report types require the simulated released INITIAL under the invented fixture rules. data/README.md is the grammar/routing explanation; it explicitly disclaims operational sources and validation. Local files were preserved; research does not independently certify host freeze status.

SC-01 fixes the return loop, R1/R2 history, six current valid route decisions, twelve accepted events, full message, audit and export bytes. SC-02 to 05 cover other types and absent JSN; SC-06 to 18 validation/permission failures; SC-19 replay; SC-20 invalidation; SC-21 competing edits; SC-22 inert instruction-like content; SC-23 recovery; SC-24 independent cases for every role's actions; SC-25 export consistency. Scenario references to SC-01 prefixes and SC-24 alternatives must run independently, not be concatenated. Literal fixed outputs are oracles for tests, never runtime lookup answers.

Concrete integration risks for planning:

- Reconciliation uses `{id,recordId,parents,actor,value}` with value string/null, whereas fixtures use structured snapshots, primary parent and merge parents. A lossless adapter is needed; explicit merge parents must be de-duplicated because R4's primary parent is also a merge parent. Canonical content serialization and revision identity must prevent replay/content collisions. Toolkit bounds (5,000 revisions per input array, 50,000-character value) need explicit application limits/errors. No toolkit result may silently select a conflict winner.
- Toolkit ID ordering differs from fixture chronological revision history and audit sequence. Retain domain sequence separately. Audit attribution, actor role and revision-bound approval validity are not encoded by reconciliation. R3A remains accepted while R3B is retained; CONFLICT blocks review/release until confirmed resolution creates R4 referencing both heads.
- Fixture operation replay is more than merge idempotence: identical operation/payload returns its stored result without duplicate events, while a new duplicate approval attempt is rejected. Rejected attempts belong in a separate attributed stream, preserving accepted audit and holder. Error precedence is specified in data/README.md and must survive adaptation.
- SC-23 requires acknowledged checkpoints to survive reload/restart and failed writes to preserve draft/route without false success. Foundation and offline primitive provide no storage. Persistence boundary, atomic commit semantics, restart behavior, retry journal and recoverable failure injection remain decisions for planning. Local stale-edit demonstration is not distributed synchronization or encrypted storage.
- SYN-CASREP-1 requires exact field order, LF endings, terminal LF, NONE handling and multiline outputs; exports must agree with the released revision and must not create events. Field values exclude CR/LF and the equipment delimiter as documented. UI changes must not silently normalize fixture bytes. Arbitrary comments must remain inert text.
- Demonstration actor selection is not authentication. Backend checks must enforce the selected synthetic actor/role and current holder; UI disabled buttons alone are insufficient. Actual authentication, approved permission rules and tamper-resistant operational audit remain unverified.
- Current fixtures define linked UPDATE/CORRECT/CASCOR, frozen released content and fresh review. The workflow skill also calls out cancellation, expiry and supersession: no authoritative operational semantics or separate fixture cases for these were inspected. Planning must explicitly address their applicability and any disclosed synthetic lifecycle behavior without inventing Navy policy or removing the four named types.
- Missing NWP edition/format rules and sponsor samples prevent a real-format validation claim. Keep the warning visible in UI, exports and documentation. Label checks cannot certify free text as unclassified. JSNs demonstrate a fictional relationship, not 3-M connectivity.
