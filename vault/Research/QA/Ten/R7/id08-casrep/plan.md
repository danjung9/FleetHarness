# Durable local work and recovery

storage.mjs uses an app-specific OS temporary directory and browser-generated random workspace key. Store the operation journal, full derived workspace, rejection/replay registry and monotonically increasing checkpoint version. Write a new temporary file, fsync, atomically rename, then acknowledge; preserve last complete checkpoint on failure. Serialize writes per workspace and compare expected checkpoint versions. GET /api/workspace?key=<key> returns {version:integer,operations:array,records:array}; missing workspace is version 0 with empty arrays. POST /api/workspace takes {key:string,expectedVersion:integer,operation:object,failBeforeCommit?:boolean}; it applies the shared reducer to the existing server journal rather than trusting client-supplied approvals/history. Success returns {ok:true,version:integer,record:object}; conflict returns HTTP 409 {ok:false,error:"Workspace changed; reload and review.",version:integer}; injected/real precommit storage failure returns HTTP 503 {ok:false,error:"Save failed; draft retained. Retry when storage is available."}. These are local workspace storage responses, separate from /api/invoke's frozen computational envelope. The key is an isolation token, not a security boundary or account.

Browser localStorage saves pending fields and queued disconnected edits before showing Pending locally. Save means backend checkpoint acknowledged. On reload show unsaved/pending work distinctly over the last committed revision. Role/tab changes preserve drafts. Every retry keeps the same operation ID. No network means edit/queue only: the server remains the sole computation authority. Reconnect simulator is labeled and submits the original base revision; acknowledged journal and queued work survive service restart. Local plaintext storage is neither device encryption nor a validated retention design. Retain until explicit confirmed reset/export; document OS temp cleanup risk and local-only scope. Production requires an approved durable datastore, backup/retention policy, authenticated transport and receiver acknowledgements. There is no byte-transfer transport obligation, so do not add a fake upload meter or claim chunk planning is delivery.

Disconnected-copy UI: when root R1 is saved, reserve detached edit ID R3 while the online next save creates R2. Display offline label and base revision. Reconnect retains R2 and R3, shows both complete field values and a conflict, blocks submission, and lets the originator select/edit merge content. Confirming both reviewed heads creates R4 with R2 primary parent and sorted merge parents R2/R3. Do not merely preserve revision IDs invisibly. SC-21 independently uses its own fixture revision IDs R3A/R3B/R4. The two examples test the same general rule.
