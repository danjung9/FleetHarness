## Prepared data fit and parser mismatch

`inputs/manifest.json` version 1 declares mode synthetic and an empty sources array. The generated data now exists: 13 records and 14 scenarios, with provenance, unchanged rawText, selected day/ship, category-specific answer keys, UTF-16 evidence, expected flags, non-events, timeline order and export expectations. The largest raw message is 320 lines and 26,807 UTF-16 units, below the existing primitive's 200,000-unit text bound; HTTP request limits are still unknown.

SYN-OPTASK/1 has three headers plus slash-delimited `FREQ`, `CRYPTO`, `FLIGHT` and inert `RMKS` sets. FREQ includes net, channel, frequency literal/unit and a window; CRYPTO a fictional change-over ID/window; FLIGHT an instant with no fabricated duration. The current toolkit recognizes only positional EVENT/TASK records. Feeding these fixtures unchanged to that parser cannot provide the required named outputs. Converting them first into EVENT/TASK would also discard category fields and jeopardize exact original spans. Reuse the foundation and appropriate primitive mechanics, not a lossy intermediate grammar or canned fixture results.

The data README reports preparation checks of 413 evidence slices and fixture arithmetic. This research inspected those claims and record structures but did not rerun that validation or establish host freeze status. Fixture checks are not application verification. Embed the exact needed supplied raw sample strings/scenarios in the self-contained index.html without fetching local JSON; do not ship answer-key data as runtime extraction logic. Later planning must distinguish sample reuse from separately authored held-out evaluation.

Concrete coverage already available: complete all-category/two-ship overlap; 320-line dense input; cross-midnight clipping and equivalent explicit offsets; out-of-day events; CRLF/repeated labels; emoji/accent before evidence; missing zone; impossible date; reversed/missing windows; unsupported set; duplicate ID; empty/non-string input; inert instruction-like remarks; corrected recovery. The documented duplicate policy keeps the first valid ID and flags later occurrences. Calendar day is UTC, half-open; extraction order is source order, visible timeline order original UTC start then ID. These are fictional assumptions, not operational rules.

## Integration risks and concrete options for planning

1. **Source fidelity:** preserve raw string bytes/line endings in data and original string indices at runtime. Browser textarea newline normalization can invalidate precomputed CRLF offsets; evidence must be computed against the exact runtime input retained for review/export. Token offsets must not use repeated-label search, UTF-8 byte counts or code-point counts. Derived categories/times need source references as well as displayed values. MSG-01 remains unverified.
2. **Domain completeness:** a generic event row cannot represent the three named category field sets. Dense-message non-events, other-ship extraction, overlapping intervals and point events all matter. UI review edits must preserve the original and distinguish corrections from quoted source. Existing service scaffolding supplies neither this behavior nor a usable timeline.
3. **Time and protocol:** missing zones and invalid dates must stay unresolved. Do not infer overnight rollover. Match independent clipping/minute/order expectations, retain original times and expose continuation. Multiple simultaneous validation failures and malformed headers have unspecified precedence in public fixtures; planning must document deterministic synthetic choices, output shapes, status/error literals, ordering and timestamp serialization before freezing contracts.
4. **Offline:** recommend external-network independence with the declared local service available. This is consistent with the mandated local foundation and requires no remote fonts, APIs or data fetches. Fresh parsing and reviewed export must work under that boundary; a rendered cached timeline is insufficient. A service-only UI will fail if the browser loses loopback connectivity or the service stops. Full browser-only use would require a different justified foundation/shared-core arrangement, not a duplicate parser or silent fallback. Planning must state the boundary explicitly and retain MSG-05 as unverified until exercised.
5. **Review/export recovery:** stale results after editing, silently omitted invalid sets and exports detached from review state are material risks. Exact original text, evidence, original/UTC times, unresolved items, selection and synthetic disclaimer must survive export. JSON is a lower-effort candidate for retaining nested evidence than CSV; final serialization and retention behavior belong to planning. Local acknowledgment is not operational authorization.
6. **Runtime packaging:** copied pack files must be declared in the clean-runtime allowlist without relying on `.fleet`; use the host-provided HOST/PORT and native service contract. Foundation manifests and any added dependency locks need later inspection. Sample embedding must coexist with the materialized public/index.html path rather than reconstructing a parallel application. No installed third-party dependency is required by current research.
7. **Evidence:** public fixture success alone does not satisfy MSG-04. Independent held-out cases including non-events, changed values and boundaries must establish complete response correctness and category precision/recall. Proposed 100% deterministic correctness and dense-message timing targets are scope proposals, not source-published metrics or measured results. Application Node checks, host computational evaluation, real browser journeys at both widths, host-recorded visual review/recheck and human semantic review remain separate gates.

No material owner decision blocks research. Export serialization, draft persistence and validation precedence are routine planning choices under documented synthetic assumptions. Official USMTF revision, SME mapping, real ship/amendment semantics and operational review authority remain future validation questions; no real-format claim can be made from this dataset. A later requirement for service-free offline execution would materially alter the foundation recommendation.
