Research date: 2026-11-05. Phase: research only. Recommendation, not an implementation plan or acceptance result.

## Recommendation and preserved boundary

Recommend **adopt `node-service` version `1.0.0`, adapt computation pack `offline`**, matching `.fleet/foundation-catalog.json`. It supplies the local HTTP adapter and shared JavaScript computation entrypoint without third-party application dependencies. Extend the host-materialized backend after planning; do not recreate the starter. Recommend **adapt IndexedDB** for durable browser state. **Reject PouchDB/CouchDB as a dependency for this bounded synthetic prototype**, while retaining it as an evaluated deployment option if an owner later selects CouchDB-compatible infrastructure.

This recommendation covers both tracks: handwritten training-log review, requisition and correspondence completion; a week of email/document tasking, verified actions, draft status updates and cited filing. Reconciliation alone does not cover the challenge. No scope, requirement, source fixture or acceptance ID is changed by this research.

Preserve the primary deferrals already recorded in `scope.md`: UC36-4; EVAL36-3, EVAL36-5, EVAL36-6; DELIVERABLE36-1, DELIVERABLE36-2; DESC36-2, DESC36-11, DESC36-12, DESC36-16; SCOPE36-25 and SCOPE36-26. Device/platform integration, actual timing/impact, panel/judge decisions and owner-authorized pilot/release remain unverified. Their full original wording, concrete dependencies and required synthetic coverage remain in scope. Missing official formats or experts do not justify omitting synthetic behavior. No cloud/government endpoint, actual submission, records disposal, deployment or delivery is authorized. Owner approval remains a later delivery/deployment gate.

## Concrete integration risks and handoff questions

1. **Revision-schema mismatch (OFF-01 to 03).** Fixtures use operationId/revisionId, parentRevisionIds, replicaId, object payloads and deleted flags; toolkit uses id, parents, actor and string value or null. An explicit stable adapter is needed. Preserve operation identity/content collisions and all source/audit metadata; JSON serialization must not silently erase distinct operations. Fixture payloads are partial domain values, so stringifying the latest patch alone cannot reconstruct earlier fields. Tombstones remain retained history.
2. **Missing history and delivery order.** Toolkit rejects a missing parent and cycles/cross-record ancestry. Shuffled fixture delivery expects child-first operations retained pending parent arrival. The application needs a durable pending-history boundary and retry behavior that preserves the original queue on errors. Toolkit rejection alone is not the required convergence workflow.
3. **Priority inversion and acknowledgement accounting (OFF-04).** Fixture criticality 0 precedes 1; toolkit sorts priority descending, then age, then ID. Explicitly map criticality to priority and make the fixture's ID tie-break compatible with age handling. Initial budget 300 must allocate 100 critical bytes then scan bytes 400 to 599; next 300 allocates 600 to 899. Do not advance offsets merely because `planUploads` proposed bytes. Its `pendingIds` projects the post-plan position, not durable receiver acknowledgement. Resume offsets, actual synthetic content bytes and final SHA-256 need separate integration evidence.
4. **Persistence and offline meaning (UC36-1, OFF-05, EVAL36-4).** Existing scope defines upstream disconnection after local initialization, with local-service availability to be made explicit. Browser IndexedDB alone does not make the HTML reloadable without its local server, and the foundation's fetch client alone does not save offline edits. Planning must state the exact demonstrated outage and retain one computational implementation for interface/invocation. No duplicate browser-only reconciliation engine or silent service failure fallback. Stable origins matter: changing host/port changes the IndexedDB origin. Quota eviction, failed writes and interrupted transactions must preserve drafts/export recovery and never acknowledge an unsaved edit.
5. **Review, routing and receipts (UC36-2/3/6).** Bind approval to exact current revisions; new heads, edits or source changes invalidate it. Distinguish queued offline, transferred, received and filed. A local synthetic receiving inbox must acknowledge once, retain receipt identity on replay and preserve audit history. Role strings are not authenticated identities; audit JSON is not inherently tamper-proof. No automatic connectivity-triggered transfer may override EMCON hold, cancel or review gates.
6. **Source fidelity (DESC36-7/8, EVAL36-1/2).** Display embedded training image and preserve uncertain transcription for explicit confirmation. Parse supplied constrained message/document formats rather than copying expected answers. Retain amendment, duplicate-forward, no-action and conflicting-owner/date evidence; timestamps cannot choose an authority. Preserve all four verified actions, four status drafts and all 16 cited filing entries. Unknown categories stay on hold; no actual disposal. Imported data must be treated as inert text, with malformed import leaving draft/queue/audit intact.
7. **Security and platform boundaries.** IndexedDB is not certified encryption. A future operational design needs validated device/key management, authenticated transport, receiver guarantees, retention policy, identity and an owner-selected low-code/device environment. No such integration is exercised or implicitly deferred synthetic functionality. Visible synthetic provenance is required in UI, exports and documentation.
8. **Evidence limits.** Fixed fictional timings establish 7 minutes per packet and 0.7 hours over six packets only; none are observed application/manual timings. Real baseline, error reduction, Sailor-panel judgment, official scores and deployment authority remain unresolved. Application tests must invoke the eventual actual shared code; browser journeys must establish reload/review/exchange and recovery. Host core evaluation, clean-runtime/browser gates and visual review remain later obligations; helper/tool tests cannot substitute.

No material user decision blocks research: scope already authorizes a local synthetic demonstration and excludes operational endpoints. Planning must resolve the service/outage boundary and public invocation details within that scope, carry every canonical acceptance ID and existing primary deferral forward, and fix independent complete outcomes before implementation. Actual forms/platform/keys/endpoints, SME measurements and pilot authority remain documented operational questions, not invented choices. No implementation plan, foundation-plan, application code or frozen acceptance artifact was created in this phase.
