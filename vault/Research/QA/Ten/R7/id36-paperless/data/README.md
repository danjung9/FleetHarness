# Paperless Underway synthetic fixtures

These are fictional intake fixtures for challenge 36, **synthetic, not validated against the real format**. No attachments were supplied (`inputs/manifest.json`, `sources: []`). No operational records, official blank forms, external services or personal information were used. Source requirements came only from the local `requirements.md`, `scope.md` and `.fleet/packet.json` snapshot; the challenge citation is https://cdao.hackathon.maximus.com/event/norfolk/use-cases/36 (not retrieved during preparation).

The two required files are sufficient: all source documents, emails, the training image and transfer bytes are embedded in `synthetic-data.json`. No accompanying image file, network fetch or toolkit reference fixture is needed. These fixtures precede application code. They are independent expected examples, not evidence that an application works. Host validation and freezing remain required; owner approval before delivery/deployment is a separate later gate.

## Container and record schema

The top-level object has `classification` (string, always `synthetic`), `useCase` (string), `fields` (array of name/type/description declarations), `records` (array), `scenarios` (array), and `limitations` (array of strings). Schema version 1 is recorded in every record's `annotations.schemaVersion` (number). Each regular record contains exactly the eight declared fields:

| Field | JSON type | Meaning |
| --- | --- | --- |
| id | string | Stable fixture/source identifier |
| recordType | string | Nested-schema discriminator below |
| unitId | string | Fictional unit, always UNIT-DEMO-36 |
| sourceCriterionIds | array | Strings identifying relevant canonical acceptance criteria |
| provenance | string | Synthetic and invented-format disclosure |
| input | object | Source material or inputs, not instructions to execute |
| expected | object | Fixed independent normalized outputs, issues or outcomes |
| annotations | object | Evidence, limitations and schema version |

Arrays preserve their written order unless a scenario explicitly changes delivery order. All date-times are ISO 8601 UTC strings with `Z`; calendar dates are `YYYY-MM-DD`. Quantities and minutes are numbers, counts/offsets are nonnegative integers unless deliberately invalid. No names, service numbers or real addresses are present. Role addresses use reserved `.invalid` domains. Identifiers describe fictional roles and devices, not people.

## Nested schemas and input formats

All fields below are required when present in a discriminator's fixture; optional evidence metadata is annotated explicitly. Objects have the literal keys in the JSON; there is no hidden schema or external authority.

- `training_log` (TRAIN-001): input contains `mediaType`, `imageDataUri`, `transcriptionMechanism` (strings), `widthPx`/`heightPx` (numbers), `draftFields` (object), `confirmedFields` (array of field-name strings). The data URI contains an original 900 × 370 SVG image with manually constructed blue pen-stroke paths for date, activity and duration; printed labels disclose fiction. This is a facsimile, not a real scan or official NAVPERS layout. The final digit has an overlapping stroke. Ground truth is 45 minutes; the draft says 47. A reviewer must inspect the image and explicitly confirm 45. No OCR implementation or measured OCR confidence is claimed.
- `supply_requisition` (SUPPLY-001): input `mediaType`/`rawDocument` (strings) and `draftFields` (object). UTF-8 text has one `Label: value` per line and an initial synthetic heading. It is an invented stand-in, not DD 1348-1A. Raw quantity -2 is deliberately invalid domain content inside a structurally valid regular record; correction is 2 EA of DEMO-FILTER.
- `correspondence` (CORR-001): input `mediaType`/`rawLetter` (strings), `availableEnclosures` (array), `draftFields` (object), `recoveryEnclosure` (object with id/mediaType/rawDocument strings). The letter references ENC-001, initially absent. Its exact embedded recovery text must be attached before review. ENC-001 is a nested source identifier, not a separate regular record. Layout and checks are invented, not SECNAV M-5216.5 validation.

Form normalized fields are `formId`, `unitId`, `roleId`, `date` (strings). Training adds `activity` (string), `durationMinutes` (number); supply adds `item`, `unitOfIssue`, `purpose` (strings), `quantity` (number); correspondence adds `addressee`, `subject` (strings), `enclosureIds` (array of strings). Form `expected` objects contain `correctedFields` (object), `completedDocument` (exact UTF-8 string), `initialIssues` (array of code/field/message string objects) and `reviewRequired` (boolean); training also has `groundTruthFields` (object).

Evidence uses source IDs and half-open character `span` objects: start/end (numbers, zero-based Unicode code-point indices in the source string), quote (exact string). Embedded tasking/document text is ASCII so these indices also agree with JavaScript UTF-16 indices. A `bboxPx` is [x, y, width, height] in source image pixels, origin upper left. Confidence numbers range 0 to 1 and are fictional review hints, not calibrated probabilities. Evidence must stay attached after correction; source text must not be overwritten.

- `tasking_email` (MAIL-001 through MAIL-010): input `mediaType` and `rawMessage` strings. Each complete message has From, To, Date, Subject and Message-ID headers, a blank line, body and trailing newline. This constrained RFC-like text is not a general MIME/email standard parser specification. Expected fields: messageId/body (strings), isNoAction (boolean), duplicateOf (string, empty means none). Annotations provide a bodySpan and timezone. The ten messages span Monday 2026-11-02 through Friday 2026-11-06.
- `status_document` (DOC-001): UTF-8 `rawDocument` and `mediaType` strings; expected statuses is an action-ID-to-status object. Evidence spans independently support A-002 complete and A-001 in_progress.
- `verified_action_list` (TASK-WEEK-001): input messageIds/documentIds (arrays of strings), reviewerRole (string). Expected actions is an array of four objects, each with actionId, owningRole, dueAt, timezone, actionText, status, reviewerDecision, draftStatusUpdate (strings), sourceIds (string array), sourceSpans (sourceId/span object array), unresolvedQuestions (string array). Expected also supplies actionCount (number), beforeReviewerDecisions (actionId/code/question object array), ignoredNoActionIds/duplicateForwardIds (string arrays).

MAIL-003 forwards MAIL-001 and creates no additional action. MAIL-004 explicitly amends A-001's due date from November 9 to November 10 at 16:00Z. MAIL-005 leaves ownership ambiguous. MAIL-006 is no-action FYI. MAIL-007 and MAIL-008 are contradictory peer due dates for A-004; timestamps alone do not resolve them. MAIL-010 proposes a fictional reviewer decision for A-003 and A-004, which the application must still explicitly ask the reviewer to accept. The answer key has four actions, four exact draft status strings and no unresolved questions **after** these decisions. Before acceptance, ownership/date ambiguities block verification. Source messages and competing instructions remain retained.

- `records_schedule` (SCH-DEMO-1): input rawDocument/mediaType strings. The embedded plain-text excerpt defines TRAINING, SUPPLY, CORRESPONDENCE and TASKING categories and UNKNOWN holding behavior. Expected filingManifest contains 16 objects with recordId, scheduleId, category, destination (strings), ruleCitation (span object), disposalAuthorized (boolean, false); unknownCategoryBehavior is a string. The 16 destinations cover three forms, ENC-001, ten emails, DOC-001 and TASK-WEEK-001. Supply files to DEMO/Supply/2026. Retention expressions are fictional relative review periods; dates of fulfillment/closure are not supplied and no expiration date is inferred. No real disposal is authorized.
- `reconciliation` (SYNC-001): input operations/reviewerMerges (arrays), replayOperationIds/shuffledOrder (string arrays). Every immutable operation has operationId, recordId, revisionId, replicaId, timestamp (strings), parentRevisionIds (string array), payload (object), deleted (boolean). Parent lists form causal history. Payloads are partial domain values for the stated record, not generic replacement documents. Two replica IDs are TABLET-DEMO-A and DESK-DEMO-B. Tombstone SU-2B has an empty payload and remains in retained history. Duplicate operation IDs have identical content; replay must have no extra effect.

Expected reconciliation fields: beforeMergeHeads (object mapping record IDs to revision-ID arrays), conflictCount/uniqueOperationCountBeforeMerge (numbers), canonicalRecordsAfterMerge (array of recordId/headRevisionIds/deleted/payload objects), retainedRevisionIds (string array), mergeDecisions (recordId/reviewer/reason string object array), approvalAfterNewHead (string). Canonical records are lexicographically ordered by recordId; head lists are lexicographically ordered. Nine unique initial operations yield two conflicts: training edit/edit and supply edit/delete. Sequential TR-1→TR-2 is not a conflict. CORR-001 and TASK-WEEK-001 are unrelated records. Two explicit reviewer merges consume both conflicting heads and retain all 11 revisions. Reordered delivery can encounter a child first: retain it pending parents, then converge. No timestamp winner may silently discard a head. Final supply quantity 2 is an explicit reviewer correction, not an automatic merge inference.

- `transfer` (TRANSFER-001): input attachments (array), budgetBytes (number), ordering (string), events (string array). Each attachment has attachmentId/recordId/revisionId/contentBase64 (strings), criticality/totalBytes/acknowledgedOffset (numbers). Priority 0 precedes priority 1; tie-break by attachment ID. Offsets and budgets count decoded raw bytes, excluding protocol overhead. ATT-CRITICAL is exactly 100 `C` bytes tied to CO-1. ATT-SCAN is exactly 1000 deterministic binary bytes tied to TR-4, **a transfer stand-in, not the training image**. Its first 400 bytes are assumed already acknowledged at scenario start. Actual image bytes remain separately available in TRAIN-001.

Expected firstAllocations/resumeAllocations are arrays of attachmentId (string), startOffset/bytes/nextOffset (numbers); remainingScanBytesAfterResume and standaloneScanAt400Budget300NextOffset are numbers; contentSha256 maps attachment IDs to hex digest strings. Initial 300-byte budget spends 100 on critical content then 200 on scan (400→600). Resume with 300 advances 600→900, leaving 100. The isolated scan-only case advances 400→700. Bytes scheduled are not acknowledged until receiver confirmation; an interruption must retain actual acknowledged progress and final content must match the digest. Metadata calculations do not establish working application transport.

- `routing_packet` (PACKET-001): input packetId/reviewerRole/recipientId/routeOperationId/receiptId (strings), recordRevisionPairs (array of recordId/revisionId string objects). Expected auditSequence is an ordered array with sequence (number), at/actorRole/event/packetId (strings), revisionSet (string array). The fixed sequence is captured, validated, corrected, conflicts_resolved, approved, queued_offline, emcon_hold, exchange_permitted, transferred, received, filed. These fictional timestamps describe an expected example, not actual application logs. Expected receipt has receiptId/routeOperationId/recipientId/packetId/receivedAt strings. inboxCountAfterReplay is 1; offlineState/finalState/filingManifestRecordId are strings; remoteDeliveryClaim is false. Queueing while disconnected is distinct from transfer, receipt and filing. The only recipient is a local synthetic inbox. Approval is bound to the four current revisions; edits or new heads require review again.
- `synthetic_measurement` (METRICS-001): all counts/durations in input and arithmetic in expected are numbers, intendedUses is a string array, timingProvenance and expected realManualBaseline/actualHoursReturned/actualErrorReduction are strings. Durations are seconds; all manual **and demo** timings are invented, not observed. Six packets × (720−300) seconds = 2520 seconds = 0.7 hours. Three seeded form issues caught / three = 100%. Fictional rework packet count 2−0 = 2. These numbers establish arithmetic only, not Fleet impact.
- `synthetic_review` (REVIEW-001): input reviewerRole/fictionalAssessment (strings), rubricWeightsPercent (object of numeric percentages), milestonesDays (number array). Expected panel/scoring/device/platform/pilot/release statuses are strings; milestones is an array of day (number), action/status (strings). Official rubric weights total 100, but no scores, Sailor-panel endorsement, device certification, owner decisions or deployment approval are invented.

## Declared fictional checks and recovery

Required form IDs, role/unit IDs, date and identifying activity/item/subject fields cannot be blank. Dates must be valid calendar dates in the stated representation. Duration must be positive whole minutes and an uncertain value requires explicit confirmation. Supply quantity must be a positive integer; only EA is used here. Referenced enclosures must be attached. Actions require one accepted owner and one UTC due date. Unknown filing categories hold for review. These are deliberately narrow synthetic rules; no operational or official-format authority is implied.

Each scenario contains `name` (string), `kind` (typical, edge or invalid), `input` (object) and `expectedBehavior` (string). Inputs reference stable record IDs and may override fields or deliberately violate nested/domain schemas. They must not replace the regular source record. The 23 scenarios include:

- Typical: complete both tracks with exact documents/actions/drafts/filing; calculate labeled synthetic metrics.
- Edge: replay and shuffled delivery, interrupted transfer, exact/zero budget, fully acknowledged transfer, offline restart and duplicate receipt.
- Invalid/recovery: blank item, negative quantity, missing enclosure, uncertain handwriting, contradictory due dates, ambiguous owner, malformed JSON, unknown filing category, pending/stale approval, quota failure, excessive/negative offsets, EMCON hold and cancellation.

Every invalid scenario specifies a literal error code/message, preserved draft/source/queue/audit state, a corrective action and a successful end state. “Invalid” includes invalid workflow transitions and simulated failures, not only JSON type violations. No draft should be lost on validation or import failure. Storage-write failure must not report success; the unsaved draft is retained for export/retry. EMCON hold must send zero bytes despite connectivity. Cancelled exchange stays stopped until explicit resume. Duplicate receipt produces one inbox item. The complete fixture outputs referenced by scenarios are literal independent answer keys, not just record titles.

## Downstream use and limits

Reuse these exact sources and scenarios in planning, sample data and application tests after host freeze. Embed needed fixture content into the self-contained index.html so loading samples does not fetch local files. Keep synthetic provenance and format limitations in the interface, exports and documentation. Preserve these files rather than changing expected answers to fit implementation. Test actual persistence, recovery, image review, routing and byte transfer independently; pure reconciliation/scheduling checks are insufficient.

Actual forms/versions, authoritative validation rules, routing chain, records schedule, SME baseline, device/browser/platform support, identity, encryption, permitted transport and owner/pilot approval remain unresolved. All source criterion references identify fixture intent, not completed acceptance checks. No application research, architecture, implementation, deployment or delivery was performed in this phase.
