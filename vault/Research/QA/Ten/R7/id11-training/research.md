## Concrete computation mismatches

Source inspection, not an executed dependency test, establishes these gaps:

- **Input grammar:** primitive accepts `windows`, `people`, `requests`; fixtures use `operationalWindows`, `personnel`, `drills`, policies, history, departments and occurrences. Conversion must retain every constraint and preserve negative pre-week history. The toolkit validation uses nonnegative integers by default, incompatible with directly passing negative history.
- **Personnel selection:** primitive requests specify exact `people`; qualification coverage is a set-membership check. Fixtures require choosing among eligible personnel, distinct people per counted role, and qualification validity throughout the interval. P9 is a valid Tuesday EOOW alternative; expired P8 is not. Merely renaming fields cannot implement this.
- **Resources:** primitive treats resource strings as exclusive tokens without a resource roster, availability or reference validation. Fixtures require known resource IDs and whole-interval availability, all with capacity one.
- **Fatigue/history:** primitive considers only searched assignments and a single whole-horizon `maxMinutes`. It lacks fixed watches, pre-week rest, per-UTC-day splitting and weekly clipping. WATCH-P1 precedes the week; WATCH-P5 adds 60 weekly duty minutes. A single reduced weekly budget cannot enforce all daily/rest rules.
- **Recurrence:** primitive explicitly infers no recurrence. Fixture occurrence lists are authoritative demonstration obligations; `referenceIntervalMinutes` is descriptive metadata. Do not derive a conflicting second obligation list. Check releases, completion deadlines, both DC occurrences, historical overdue and future obligations separately. Real SFTRM mapping remains unverified.
- **Search protocol:** primitive accepts maxNodes 1 to 200000 with default 50000; fixture zero is a valid deliberate exhausted-search input and base budget is 10000. Primitive returns `budget_exhausted`; fixture vocabulary is `search-exhausted`, plus `invalid-input` and `cancelled`. Planning must specify the complete public response/error mapping and array ordering, not silently change fixture meaning.
- **Ordering and negotiation:** primitive sorts requests by candidate count then ID and starts numerically. Fixture preference is department priority, drill ID, preferred start then ascending alternatives and personnel IDs. Departmental ownership, counterproposals and preference measures are absent. Avoid promising a literal internal search trace from a post-hoc canned transcript.
- **Cancellation:** primitive checks an AbortSignal inside synchronous recursion. A blocking HTTP event loop cannot necessarily receive a cancellation request during that recursion. A bounded, interruptible execution mechanism needs an explicit planning decision; aborting the fetch alone does not establish server cancellation.
- **Outputs/state:** primitive lacks original-proposal collision reports, per-day heatmaps, occurrence summaries, immutable last-valid-board protection, revisioned review, persistence, exports and reset recovery. All remain application responsibilities. Diagnostic search reasons are observations, not a minimal unsatisfiable core.

Recommendation is to extend the materialized backend computation rather than build a competing browser solver. The UI and evaluator must invoke the same computation; application tests must import it. Never modify protected `.fleet/toolkit` source. Limits currently include 24 requests, 200 people, 100 starts per request and 200000 search nodes; these are source bounds, not performance measurements or recommended operational capacities.

## Fixture evidence and domain limits

The base is UTC `[0,10080)` from 2026-11-09T00:00:00Z, with half-open intervals. Fictional policy is 480 minutes minimum rest, 600 duty minutes per UTC day, 1200 per displayed week. Those are supplied synthetic assumptions, not owner-approved rules.

The hand-derived oracle places DC-1 at 540, ENG-1 at 1980, WPN-1 at 780, CS-1 at 2220, AIR-1 at 3420 and DC-2 at 6300, all 120 minutes long. Initial DC-1/ENG-1 produce two collision entries: P1 and ROOM. Engineering changes its proposal; Weapons and Combat Systems retain theirs. P1 and P2 each train 360 minutes; P3 to P7 each train 120; P8/P9 train zero. Total training is 1320 personnel minutes; displayed-week duty is 1380. Six obligations are due and scheduled with zero missed in the base. These are supplied independent reference values, not executed application results.

Boundary variants include rest 480/479; weekly limit 360/359; daily fixed-history limit 540/539; qualification expiry at end versus one minute early; deadline 2340/2339; historical completion -600 versus -2000; and zero assignment attempts on a known feasible input. Preserve feasible-current-week plus historical-overdue warning semantics instead of misreporting complete historical satisfaction. Grammar is invented and history is limited to one completion timestamp per requirement. No daylight-saving calendar, rolling fatigue windows, partial credits or certification model is supplied.

## Handoff risks and open questions for planning

No missing owner decision blocks this research: synthetic policies and finite fixture scope are explicit. Real policy/data and operator authority remain operational gaps. Routine choices belong to planning, without broadening or narrowing requirements:

- Resolve HTML fixture embedding with the catalog's `public/index.html` service layout. The shell can embed sample inputs and still use `/api/invoke` for all computation; self-contained samples do not imply standalone offline scheduling.
- Define exact protocol/status/error precedence, deterministic output ordering, input size limits and behavior for unsupported formats. The host's generic schedule evaluator only understands the smaller toolkit grammar and nonnegative minutes; it cannot alone verify this richer PB4T workflow. Additional appropriate exact/numeric capability evidence is needed under the public protocol.
- Define a measurable bounded deconfliction objective and before/after measures. A feasibility witness is not proof of global optimization. If the planner requires objective optimization, independent bounded objective evidence is necessary; do not erase the source's one-click optimization deliverable.
- Specify cancellation, preservation of last valid allocation, local persistence and revision reset behavior. A service foundation supplies neither durable state nor owner acceptance.
- Preserve all canonical IDs: UC11-1, SCH-01 to SCH-05, DELIVERABLE11-1, DESC11-1 to DESC11-3, SUMMARY11-1, SCOPE11-4 to SCOPE11-7 and SCOPE11-9. Source headings/provenance IDs must remain accounted for without inventing features. Primary deferrals need full source-linked synthetic coverage; SCH-05 remains human evidence.
- Freeze independent literal outcomes before implementation; carry application function tests and actual desktop/narrow browser journeys forward. Pairwise interval/duty checks, computed heatmaps and recovery outcomes matter. Host computation/browser/visual gates and later owner review remain separate from fixture validation.

Research outcome: reusable setup and a useful bounded search primitive are available; the domain extensions above are mandatory to fulfill the synthetic workflow.
