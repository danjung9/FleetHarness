# Implementation plan: synthetic training draft

Planning date: 2026-11-04. Inputs: requirements.md, scope.md, research.md, .fleet/packet.json and the three assigned skills. Architecture was published with fleet_system_design before this document; system-design.json maps six application components to exact filenames. This phase produces planning artifacts only. No application code or tests have been implemented or run.

## Complete vertical slice

Open index.html directly with networking unavailable; inspect four editable requests A to D and supplied roster/windows; compute a complete feasible draft or one of three distinct failure outcomes; inspect all requests and whole-horizon loads; optionally select another allowed start and check the complete draft; mark the unchanged feasible draft reviewed; export JSON, close/reopen and import to restore exact inputs and draft with a fresh review required. No request may disappear from the board in a failure state.

Default independent expectation: A=0, B=90, C=0, D=1440, P01=120 minutes and P02=120 minutes. A ends at 60, so B=90 satisfies the supplied 30-minute rest. B=0 conflicts. This expectation comes from the brief, not a toolkit output. Whole sessions fit operating/person windows [0,240] or [1440,1680]. Day two begins at 1440; all intervals are half-open.

## Files and dependency decisions

- index.html: complete distributable with inline CSS and classic JavaScript; no imports, CDN, fetch, fonts, service worker, build server or adjacent runtime files. It includes a marked verbatim copy of the testable core and the browser controller/editor/board/file adapter.
- app-core.js: dependency-free classic JavaScript core exposing a named browser global and guarded CommonJS exports. Pure validation, solve, draft checking, loads, state transitions and snapshot functions; usable by Node and the inline app.
- core.test.cjs: actual application-core tests with independently reasoned fixtures and pairwise checks.
- state.test.cjs: review, input revision, manual draft edit and snapshot tests against actual core functions.
- packaging.test.cjs: extract and execute the marked inline core with Node vm, require byte equality with app-core.js, exercise exported default and edited workflows, and reject external runtime references. No second independent implementation in HTML.
- README.md: written after implementation, matching actual controls, local opening, save/import, test command and limitations. path-to-fleet.md: explicit fielding gaps and owner review needs. verification.md: later evidence, including browser checks, failures and limitations. The desktop runner owns test-report.json and source hashing.

Research decision retained: adapt the supplied scheduling approach, with application-specific validation and exact-input preservation; never modify .fleet/. Tool fixtures and calculations are reference material, not application evidence. Supplied toolkit version/license are unverified; do not represent reuse as a licensed production dependency. An independently written small core is an acceptable alternative if copying is unsuitable; record the actual reuse decision. OR-Tools is deferred: no dependency is needed for five default candidate choices. No model service is required. Any future model-assisted explanation is advisory text derived from deterministic diagnostics and cannot decide feasibility, modify inputs or relax constraints.

## Data contract

Use JSON-compatible plain data, schemaVersion 1. Preserve array order and exact accepted values; sorting/deduplication may happen only in a private search copy. Unknown keys, duplicate IDs/starts, malformed values and missing fields receive actionable path-specific validation rather than silent repair. Preserve raw editor text separately when parsing fails.

Input shape: `{schemaVersion:1, epoch:{label:string, day2Minute:1440}, operatingWindows:[[start,end],...], people:[{id, qualifications:[string,...], availability:[[start,end],...], maxMinutes, restMinutes}], requests:[{id,duration,allowedStarts:[integer,...],personId,roomId,requiredQualification}], maxNodes:50000}`. The epoch label is synthetic, not a real dated operational epoch. Use safe nonnegative integer minutes within the declared two-day range 0..2880, start < end for windows, positive duration with safe end arithmetic, nonnegative caps/rest and integer maxNodes in 1..200000. Exactly four unique request IDs A/B/C/D and two unique person IDs P01/P02 remain present; values, qualifications, windows and explicit assignments are editable. Required qualifications and room IDs are nonempty strings; no implicit room availability or qualification substitution. Each request has one fixed existing person, one room and a nonempty list of distinct candidate starts. No room registry beyond shared exact room IDs is needed. Empty qualification sets are structurally valid; missing coverage makes the problem infeasible. Empty available/operating window lists are structurally valid and infeasible for positive sessions. Empty candidate lists are invalid (the editor must specify a choice).

Results: `{status, origin, assignments, loads, diagnostics, explored, inputRevision}` with origin `search` or `manual` (manual only after an explicit person-selected draft edit). Status values `feasible`, `infeasible`, `invalid_input`, `budget_exhausted` have plain labels “Feasible draft”, “Infeasible with these choices”, “Invalid input”, “Search limit reached; feasibility unknown”. Only feasible has a full assignments array with `{requestId,start,end,personId,roomId}` for every request. Other states retain all requests in input and board, never expose a partial draft as complete, and never reuse previous success as current. Show proposed duration totals from valid input separately from scheduled totals; nonfeasible scheduled totals are “No complete draft”, not misleading zeros. Invalid input has field errors; search diagnostics identify request/person/room and constraint when available and are observations, not a minimal unsatisfiable core.

Snapshot: `{schemaVersion:1, kind:'synthetic-training-draft', inputText, inputs, result, draftReview}`. inputText preserves invalid editor text; inputs is null if parsing failed. Export valid and failure states. Exact round-trip means deep equality of input values/order, raw text and stored draft/result, not identical whitespace of downloaded JSON. On import validate size (1 MiB maximum), schema, values, result structure and cross-field consistency before atomic replacement; reject malformed, unsupported, stale or tampered snapshots without damaging current state. For search-origin results, recompute the deterministic result with the saved budget and compare semantic content (excluding revision counters); for manual-origin results, validate every selected assignment directly and independently recalculate loads/diagnostics without replacing the saved starts with the first search solution. Invalid-input snapshots must reproduce validation errors from their preserved text rather than requiring invalid inputs to pass validation. A claimed feasible draft must cover every request and pass independent checking. Preserve the imported draft exactly when valid. Imported review is retained as historical metadata only; current review always clears and the UI explains re-review. Export/import never establishes identity or source approval. Use textContent for untrusted display. No localStorage dependency; portable recovery is explicit file import.

## Deterministic constraints and state transitions

Validation precedes search. Solver only selects listed starts and never changes person, room, duration, qualifications, limits or request membership. Every session must be wholly inside one operating window and its person's single availability window; qualification coverage must be literal; exclusive rooms and people cannot overlap. For each person, every pair must have gap >= supplied rest in either temporal order. Duty is sum of durations over both days, including separated sessions, compared with maxMinutes.

Search in stable request/candidate order on a copy. Count one node for each attempted candidate before conflict checks; never attempt more than maxNodes. If a further candidate is needed after the allowance, return budget_exhausted. Exhaustive traversal without a full draft means infeasible; an exactly completed traversal at the allowance can still prove infeasibility. A found complete draft may be feasible at the allowance. Default maxNodes=50000; expose tiny budgets in an evaluator details panel. No interactive Stop control is planned for this bounded synchronous slice; do not claim cancellation. If later added, interruption yields unknown feasibility and cannot be called infeasible. Limits on contract size (four requests, two people, at most 100 candidates per request and 100 windows/qualifications per list) plus budget bound work; browser responsiveness still requires measurement.

Every relevant editor event immediately clears review and marks the old result stale, even if new text is invalid. Valid edits recompute after a short debounce, guarded by revision so stale completion cannot replace current data. Invalid text remains visible with its actionable error. Manual board changes may select only listed starts, clear review and validate the whole draft; a conflicting selection is visibly unresolved. No dragging to arbitrary times. Mark reviewed is enabled only for a complete independently checked current draft; store synthetic reviewer label and local timestamp, never treat it as authenticated identity. Re-solving, imports and relevant input/result edits clear current review even when values are later reverted. Changing presentation alone need not clear it.

## Ordered implementation tasks and gates

1. Establish the contract and exact default synthetic input in app-core.js; implement path-based validation. Gate: malformed values cannot reach scheduling, and original data remains unchanged.
2. Implement bounded deterministic solve, complete-draft validation and load calculations. Gate: core.test.cjs covers defaults, altered inputs, every constraint, node boundaries and independent all-pair verification. No toolkit result used as oracle.
3. Implement revision/review transitions, manual candidate selection and snapshot encode/validate/restore in the core. Gate: state.test.cjs proves invalidation and atomic rejection, including stale/tampered results.
4. Build index.html editor, two-day board, four statuses, explanations and personnel load table. Embed the exact core; add packaging.test.cjs. Gate: tests exercise the inline exports and byte equality; all requests stay visible on errors. Technical budget control stays in evaluator details.
5. Add download/file import adapters and human review controls; show persistent synthetic/draft labels and exclusions. Gate: manual procedures B1 to B5 in test-matrix.md, including offline close/reopen, must be recorded or explicitly unverified.
6. Write README.md after the finished controls exist and path-to-fleet.md with operational gaps. Report all architecture components using build-phase tools when available. Gate: omissions match brief in both UI and README; no issued-schedule or sync claims.
7. Handoff source and Node tests to verifier: `node --test core.test.cjs state.test.cjs packaging.test.cjs`. Preserve failures and use only the phase's bounded repair allowance. Record additional browser evidence in verification.md; runner manages test-report.json, integrity and hashes. Human source revision approval is a later host gate, separate from draft review.

## Risks, omissions and human requirements

Browser target is a current desktop Chromium browser for the initial manual evidence; record exact browser/OS. Other local-file browsers remain unverified until checked. File download permission and picker cancellation need visible handling. Byte equality plus VM tests do not prove DOM events, downloads, layout or accessibility; record real browser evidence. Bounded synchronous search responsiveness must be observed; if unacceptable, reduce UI scope honestly or implement chunking without changing constraint semantics and update tests.

Omit recurrence, SFTRM interpretation, departmental negotiation/agents, real readiness data, qualification policy beyond supplied values, official-calendar writes, reconnect sync, optimization guarantees and operational identity/persistence. No operational integration, including a simulated calendar connection, is part of the architecture. Two days are not a weekly board. Owner-approved fatigue, historical duty, recurrence anchors/due windows, qualification policy, authorized connectors, data handling and independent domain validation are prerequisites to fielding. Future recurrence must expand each mandated occurrence with a unique ID and due window and verify all deadlines; it is not satisfied by four feasible sessions.

A human must inspect all four sessions, constraints and loads, record current-draft review, and separately approve a particular source revision through the host. No relaxation is allowed. If generation is not accepted, only the brief-authorized clearly labeled conflict-checker fallback is possible; generation checks stay unmet and the accepting human must record reduced scope. Do not silently switch to it.
