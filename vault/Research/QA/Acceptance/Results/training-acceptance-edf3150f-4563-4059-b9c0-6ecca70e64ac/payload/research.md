## Scheduling semantics and integration risks

The default expected draft is A=0, B=90, C=0, D=1440, with 120 minutes per person. This follows independently from the brief: B=0 collides with A; B=90 leaves P01 the required 30 minutes after A ends at 60. These are expected values for later application evidence, not observed solver results.

The local solver uses half-open overlap and checks that each whole session fits a single operating and assigned-person window. Duty caps apply over the entire horizon. Rest applies against each prior assignment in either time order; zero rest permits adjacent sessions. Qualification coverage is collective across assigned people; the brief's single fixed person per request removes ambiguity here. Room strings receive exclusivity checks but there is no separate room registry or room availability model. Do not infer either policy.

The primitive returns `feasible`, `infeasible`, or `budget_exhausted`; invalid structure throws an error. A fourth, actionable invalid-input presentation is therefore an application responsibility. Cancellation throws `Schedule search cancelled.` and must not be presented as infeasibility. Nonfeasible results have an empty `assignments` array; retaining all original requests for correction is essential.

The default budget is 50,000 and the accepted range is 1 to 200,000. Static source increments `explored` per candidate attempted before conflict checks, declares exhaustion when it exceeds the allowance, and caps the reported count. This is candidate-attempt accounting, not elapsed time, all preprocessing work, or a global optimality metric. Browser responsiveness and interruption remain untested; a synchronous main-thread search may prevent an interactive stop event from being processed. Diagnostic reasons accumulate across explored branches, are capped at 100, and are observations rather than a minimal unsatisfiable core. Neither exhaustion nor a stopped run proves no solution exists.

Validation must distinguish malformed data from well-formed but unsatisfiable choices without silently repairing input. Nonempty fixed person/room assignments, four retained request identities, integer time limits and exact raw-input retention need explicit treatment beyond the generic helpers. Input import adds stale-result and false-review risks: serialized feasible assignments must not be trusted merely because they parse. Relevant edits must invalidate review, and portable state must correspond to the exact current inputs. Import review restoration policy remains unresolved in the scope; human draft review and host approval of a source revision remain separate.
