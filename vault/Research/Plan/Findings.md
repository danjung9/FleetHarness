# FleetHarness findings and rulings

## Bottom line

[R] Put one useful task in the officer's hands: check a small training draft, review the conflicts and save a clearly marked draft. [E] FleetHarness already has a substantial implementation, but this review found no verified real model build through it on the event key. [R] Keep the factory behind the task and show its actual build evidence after the app works. [E] Time saved, generated app quality, usability and offline behavior have not been measured in this review; no real model build was run here. [R] Follow the timed gates in [[Research/Plan/Plan]] and keep the partial scope visible.

## The decision that matters most

1. **[R] Submit a task result first and a software factory second. Confidence: weak for benefit, confirmed for implementation fit.** Use a partial ID 11 training draft with four synthetic requests, fixed people and resources, explicit candidate times, a conflict result and human review. The current scheduler gives this slice a concrete starting point; it does not prove this is the most valuable officer problem. Sources: `harness/tools/scheduling.ts`; [[Research/FleetHarness-MVP/Reconcile]]; all three [[Research/Council/Officer/Decision-v2]], [[Research/Council/Builder/Decision-v2]] and [[Research/Council/Judge/Decision-v2]]. Their shared model provenance is weak corroboration, not three independent validations. Reverse the choice before the scope lock only for stronger existing artifact and user evidence.

2. **[E] A real event-key build is the immediate technical uncertainty. Confidence: confirmed code restriction; successful generation not verified.** FleetHarness's Codex adapter requires a ChatGPT account and deliberately removes API-key environment variables. Pi accepts an API key for a model present in its runtime catalogue. The separate successful event-key coding session in [[Team/Now]] does not prove the Pi route can build an app. Sources: `electron/main.ts`, `electron/pi-backend.ts`, `electron/codex-rpc.ts`, `electron/codex-session.ts`, `src/ModelSettings.tsx`. [R] Set a Wednesday 4 PM hard gate for one real bounded build; do not spend the night changing authentication backends.

3. **[P] A partial local app does not meet all published requirements. Confidence: confirmed requirement, partial-entry eligibility not verified.** The full ID 11 asks for departmental agents, negotiation, qualified rosters, fatigue constraints and training periodicities. The category text for both ID 11 and ID 24 includes disconnected work, human review and reconnect synchronization; repeated general requirements reinforce sync. Local save or file transfer does not establish synchronization. Sources: verification V10, V12, V35 to V38; [[Research/UseCase-Map/PoC-Mapping]]. [R] Ask for a ruling on a disclosed partial entry. Until then, describe the omissions and leave compliance unresolved; choosing BYOI is not evidence of a waiver.

## The product and the officer

4. **[R] Name a training coordinator and a reviewing officer as the proposed users, then validate the job. Confidence: weak.** The practical question is whether four proposed events can fit the supplied people, rooms, qualifications, windows and rest limits. The event describes a scheduling problem; no current local interview establishes its frequency, burden or the right decision maker. The round 1 duty-officer message parser and a training coordinator are different jobs. Sources: [[Research/Naval-User/Users]], [[Research/Naval-User/Workflows]], verification V20 to V23. Public administrative and fatigue evidence supports investigation, not the claimed minutes saved on this task.

5. **[R] Simplicity means a completed, recoverable task. Confidence: weak until observed.** The front door should show Try example, Edit requests, Check draft, Review and Save draft. Put the supplied constraints and reason for a failed check beside the result. Preserve work through close and reopen. Technical provider choices belong with the technical operator. Sources: [[Research/Naval-User/Simplicity-Requirements]], [[Research/Interfaces/Officer-Walkthrough]], [[Research/Landscape/App-Builders/Simplicity-Patterns]]. The research's three-minute intake, five-minute result, ten-minute orientation, 30% reduction and proposed 90-second checks are targets, not measurements or Navy standards.

6. **[E] The existing scheduling tool solves a narrower problem than its use-case title. Confidence: confirmed by source.** It searches explicit candidate start times for requests with already assigned people. Qualifications are covered across the assigned group, not necessarily by every person. It checks availability, overlapping resources, person rest and minutes across the entire supplied horizon. It accepts at most 24 requests and 100 candidate starts per request, with a default 50,000-node limit and maximum 200,000. It returns feasible, infeasible or budget_exhausted. It does not infer recurrence, select a roster, optimize a schedule, apply SFTRM or negotiate between departments. Its failure explanations are encountered conflicts, not a minimal proof of inconsistency; successful results have no explanation list. Source: `harness/tools/scheduling.ts`. [R] Display the checked inputs and a verified before/after comparison instead of inventing solver explanations.

7. **[E] The message tool is not an implemented ID 24 fallback. Confidence: confirmed by source.** It parses a constrained synthetic EVENT/TASK grammar with source spans and copies an owner field. It does not establish command relevance or identify the coordinating POC from normal message traffic. Those are required in ID 24; suggested responses and calendar integration are optional. Sources: `harness/tools/messages.ts`; verification V01 to V03; [[Research/UseCase-Map/PoC-Mapping]]. [R] Do not build a second parser demo to rescue a failed scheduler. Switch only to an already accepted artifact with clearer evidence.

## The architecture and code, with file paths

8. **[E] The old compile blocker has been superseded. Confidence: confirmed as a reported test result.** The latest section of [[Research/Plan/Test-Results]] reports, at `0f175a8`, `npm test` 78/78, `npm run test:harness` 39/39 and root `npx tsc --noEmit` passing. Source inspection supports the five reported type fixes. Historical `f72c5dc` failures and manually bypassed compilation remain history, not current blockers. Desktop testing was still awaiting Electron download. Fake/scripted provider tests do not establish a real provider run or a useful generated app. Sources: [[Research/FleetHarness-MVP/Delta-0f175a8]], [[Research/Plan/Test-Results]].

9. **[E] This is an existing factory, not a README-only proposal. Confidence: confirmed by source.** There are two React front ends, an Electron host, a 34-entry catalog, ten recipe families, seven registered deterministic tools and fourteen skill documents. The run uses five sequential agent sessions: intake, research, plan, build and verify. At most one repair adds a sixth session. Review is human; delivery is host work. Seven displayed stages do not mean seven independent agent workers. Research searches supplied documents, not an independent web research service. Sources: `electron/pi-backend.ts`, `electron/agent-runner.ts`, `harness/phases.ts`, `harness/integration.ts`, `harness/catalog.ts`, [[Research/FleetHarness-MVP/Delta-0f175a8]].

10. **[E] Event-key compatibility is adapter-specific. Confidence: confirmed restriction; Pi entitlement not verified.** `electron/codex-rpc.ts` sets a separate `CODEX_HOME`, forces ChatGPT login and removes `OPENAI_API_KEY`, `CODEX_API_KEY` and `OPENAI_BASE_URL`. `electron/codex-session.ts` requires a ChatGPT account. `electron/main.ts` rejects a nonempty API key for that backend. Pi resolves a provider/model in its pinned runtime and sets a runtime API key; settings alone do not make an inference request. Blank settings default to Codex, so the operator must deliberately select Pi. Session-only key storage avoids the optional encrypted remembered-key file, but does not prove the entire process has no other inherited credentials. Sources: those files, `electron/pi-backend.ts`, `src/ModelSettings.tsx`, `package.json`.

   [V] General Codex documentation supports both ChatGPT and API-key authentication for local use. That new primary source confirms a product capability, not FleetHarness's adapter behavior: https://learn.chatgpt.com/docs/auth?surface=cli (opened November 4). [R] Do not turn the implementation restriction into a claim that Codex itself cannot use event keys.

11. **[E] Custom-tool filtering is real; execution containment is incomplete. Confidence: confirmed source, operating-system behavior not verified.** Current phase and recipe filtering limits the custom harness tools, correcting part of the older architecture critique. Pi still exposes general read, write, edit and bash tools in each phase. Workspace placement and prompt prohibitions are not an operating-system boundary. Codex requests workspace-write restrictions, no shell network and no web search, but those restrictions were not exercised here. Host verification also executes generated code. Sources: `harness/phases.ts`, `harness/integration.ts`, `electron/pi-backend.ts`, `electron/codex-session.ts`, `electron/verification.ts`. [R] A supervised, disposable preparation environment needs its own boundary and stop check; simply removing live generation from the presentation does not secure preparation.

12. **[E] Verification is useful but does not establish mission acceptance. Confidence: confirmed by source.** `electron/verification.ts` runs real `node:test` through an Electron-as-Node subprocess and checks positive passing TAP counts, zero failed/skipped/todo tests, successful exit and source hashes. It limits execution to 120 seconds and output to 2 MB. Those are meaningful controls. The model can write and repair the implementation and its tests. The checks do not supply a fixed independent answer key or drive the generated browser UI. An independently tested core file can diverge from inline browser logic. Sources: that file and `electron/pi-backend.ts`; [[Research/Architecture/Findings]], [[Research/Build-Patterns/Specs-and-Acceptance-Tests]]. [R] Accept the exact exported app against independently chosen cases, including deliberately wrong output that must fail.

13. **[E] Review and export have a remaining consistency gap. Confidence: confirmed static ordering; exploit reproduction not verified.** Approval checks a passing report and source hash, then records a review with notes of at least ten characters and prototype-only scope. It is not authenticated command approval. Export checks before waiting for the save dialog, then copies the live workspace and marks delivery without a final locked snapshot check. Changes during the dialog or copying can therefore escape the earlier comparison. Sources: `electron/main.ts`, `electron/storage.ts`. [R] Prefer an immutable reviewed snapshot with a digest. For one disclosed demonstration, terminate the worker, copy, independently accept the final bytes and record their digest; do not claim the program enforces immutability. A recheck before copying alone does not close mutation during copying.

14. **[E] There are useful controls, but no demonstrated full shutdown guarantee. Confidence: confirmed source, end-to-end termination not verified.** Renderer isolation, navigation restrictions, safe workspace file access, serialized storage writes and interrupted-run handling exist. Pi abort/dispose is not proof every descendant has ended. Test and Codex processes have process-group termination paths, but detached descendants and timing remain untested. Sources: `electron/main.ts`, `electron/storage.ts`, `electron/pi-backend.ts`, `electron/codex-rpc.ts`, `electron/verification.ts`. [R] Test Stop with a synthetic canary and observe the process tree; escalate failure to the technical operator, terminate the isolated worker environment and preserve logs. Do not claim Stop is known broken or guaranteed complete.

15. **[E] Bounded stages do not give a known time or cost for a build. Confidence: confirmed code limits, performance not verified.** Defaults include 30 minutes per stage, five minutes idle and 40 Pi turns. Five stages allow a nominal 150 minutes, or 180 with repair, before other overhead; this is arithmetic, not an observed run or guaranteed whole-run ceiling. Codex's user-turn accounting is not a model-inference cost cap. Up to three runs are supported, but the Thursday plan permits one supervised run at a time. Sources: `electron/agent-runner.ts`, `electron/pi-backend.ts`, `electron/codex-session.ts`. [R] The operator sets an earlier wall-clock deadline and an agreed spending limit; actual usage availability must be checked before promising a dollar cap.

16. **[E] Dependency-free output is a target, not demonstrated offline behavior. Confidence: confirmed contract, runtime not verified.** The build contract asks for a self-contained `index.html`, inline CSS and classic JavaScript, testable core code and tests. A scheduling module copied into `.fleet/toolkit` is not automatically a working browser app. Preview origins and the eventual exported-file origin can differ, so browser storage recovery must be tested on the delivered artifact. Sources: `electron/pi-backend.ts`, `harness/planner.ts`, `harness/integration.ts`, [[Research/FleetHarness-MVP/Officer-Test]]. Pi's `allowModelNetwork: false` runtime option does not establish offline inference. [R] Separate connected preparation, offline app use, export and future sync in every claim.
